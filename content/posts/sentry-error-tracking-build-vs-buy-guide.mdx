운영 중인 웹 서비스에 에러 모니터링을 붙이기로 하면서 Sentry 도입을 검토했을 때 정리한 내용. "직접 구축 vs SaaS 구독"의 판단 근거와, 도입 전에 알아둬야 할 비용·개인정보 이슈까지 한 번에 담았다.

---

## Sentry 한 줄 정의

Sentry = 애플리케이션에서 발생하는 에러를 실시간으로 감지·수집·그룹화해주는 오픈소스 기반 에러 트래킹 서비스. 에러 모니터링 외에 성능 모니터링, 세션 리플레이 등도 제공한다.

---

## 제공하는 서비스 종류

### ① 에러 모니터링 (Error Monitoring)
가장 기본. 버그와 크래시를 실시간 감지.
- 스택 트레이스 추적, 동일 에러 그룹화(Issue Grouping), 릴리즈 트래킹(어떤 배포 버전부터 에러가 시작됐는지)
- 단순 텍스트 로그가 아니라 에러 당시의 로컬 변수 값, 유저의 OS/브라우저 정보까지 함께 온다

### ② 성능 모니터링 (Performance / APM)
어디서 병목이 생기는지 분석.
- HTTP 응답 시간, DB 쿼리 속도, Web Vitals 측정
- 분산 추적(Distributed Tracing): 프론트에서 시작된 요청이 백엔드 어느 구간에서 느려졌는지 전체 경로 시각화

### ③ 세션 리플레이 (Session Replay)
에러 전후로 사용자가 어떤 행동을 했는지 영상처럼 다시보기.
- 클릭·스크롤·페이지 이동을 기록해 재현 어려운 버그를 눈으로 확인
- 에러 순간의 리플레이만 수집하거나, 전체 세션 중 무작위 0.1~1%만 샘플링해 비용을 통제할 수 있다 (전수 수집은 비용이 크다)

### ④ 프로파일링 (Profiling)
함수 단위 실행 효율 분석. CPU를 많이 먹는 로직을 찾아 코드 레벨 최적화가 필요할 때.

### ⑤ 크론 모니터링 (Cron Monitoring)
배치/예약 작업이 정해진 시간에 실행 안 됐거나 중간에 실패하면 알림.

### ⑥ Seer (AI Debugger)
에러 원인을 AI가 분석해 설명하고, 머지 가능한 수준의 코드 패치까지 자동 생성.

→ 실무에서 주력으로 쓰게 되는 건 ①②③, 특히 ①이다.

## 장점 / 단점

장점
- 플랫폼 커버리지: JS, Python, Java, Go, React, iOS, Android 등 거의 전부
- 문맥 정보: 에러명만이 아니라 어떤 브라우저·OS·사용자에게서 났는지까지
- 협업 연동: Slack, Jira, GitHub 등과 연동해 워크플로우 자동화

단점
- 비용: 무료 플랜이 제한적이고, 이벤트가 많아지면 비용이 급격히 증가할 수 있다 (→ 아래 비용 통제 장치로 완화 가능)
- 성능: 에러 전송 시 미세한 네트워크 부하 (비동기 처리로 최소화됨)
- 셀프 호스팅 장벽: 직접 구축하려면 권장 사양이 꽤 높다

셀프 호스팅 사양 (참고 — 이것 때문에라도 SaaS가 편하다)

| 구분 | 최소 | 권장 |
| --- | --- | --- |
| CPU | 4 Cores | 8 Cores 이상 |
| RAM | 16 GB | 32 GB 이상 |
| Storage | 20 GB (SSD 권장) | 100 GB 이상 (SSD 필수) |
| OS | Linux (Ubuntu 20.04+) | Docker 구동 가능한 최신 Linux |

## 비용 구조 (2026년 기준)

과금 기준은 주로 '이벤트(에러/성능) 수'.

1. Developer (무료): 개인용. 월 5k 이벤트 + 기본 기능
2. Team (월 $26~): 소규모 팀. 무제한 사용자, 연동 기능
3. Business (월 $80~): 고급 분석, SAML, 가시성 컨트롤
4. Enterprise: 맞춤형

소규모 팀이라면 Team 플랜으로 시작하는 게 현실적.

비용 폭주를 막는 세 가지 장치 — 이게 있어서 "비용 예측 불가" 걱정은 상당 부분 해소된다:
- Quota Management: Stats 대시보드에서 유입량을 실시간 확인, 예산 초과가 예상되면 코드 수정 없이 대시보드에서 즉시 조정
- Inbound Filters: 브라우저 확장 프로그램 오류, 구형 브라우저 오류 같은 의미 없는 에러를 수집 전에 필터링해 유료 할당량 절약
- Spend Protection: 설정한 예산 한도에 도달하면 데이터 수집을 자동 중단

## 도입 절차 (개요)

1. 대시보드에서 언어/프레임워크 선택해 프로젝트 생성
2. 프로젝트 고유 식별 주소인 DSN 발급
3. 소스 코드에 SDK 설치
4. 앱 진입점에서 DSN으로 초기화
5. 이후 에러 발생 시 대시보드로 자동 전송

## 운영 팁

- 이슈 그룹화: 같은 지점의 수천 개 에러가 하나로 묶인다 — 노이즈 관리의 핵심
- 알림 최적화: 전부 받지 말고 "새로운 이슈 발생 시", "유저 100명 이상 영향 시" 같은 조건으로 Slack 알림을 좁힌다
- 소스맵 업로드: 난독화된 배포 코드를 원본 코드 위치로 변환해 보여주게 설정 (이거 없으면 프로덕션 디버깅이 사실상 불가)
- 개인정보 비식별화: 이메일·비밀번호 같은 정보가 전송되지 않게 마스킹
- 이슈 트래커 연동: 에러 → 티켓 자동/수동 생성 (도입 안정화 후 고려)

## 직접 구축하면 안 되나? — 해봤자 만나는 난관들

서버리스 함수로 에러 수집기를 직접 만드는 안도 검토했지만, 다음 문제들이 발목을 잡는다:

1. 에러 필터링 — 의미 없는 에러를 걸러내는 기준을 직접 만들어야 함
2. 데이터 확장성 — 요청/응답 값 등 문맥 정보를 어디까지 어떻게 담을지
3. 알림 연동 — Slack 알림 기준 세분화를 전부 수작업
4. 중복 에러 그룹화 — 가장 큰 난관
   - 같은 에러가 초당 여러 번 터질 때 하나로 묶으려면? 터질 때마다 DB를 조회하면 그게 더 큰 비용
   - 어떤 해시를 만들어야 "같은 에러는 하나로, 다른 에러는 안 섞이게" 묶이는지 — Sentry가 수년간 다듬어온 핵심 로직이다
5. 소스맵 변환기 — 난독화된 배포 코드에서 원본 위치를 역추적하는 걸 직접 개발해야 함. 이게 없으면 남는 건 에러 response 문자열뿐

→ 전부 구축할 시간도 없고, 개발 비용이 구독료를 훨씬 넘어선다.

## 결론

1. 경제성: 직접 구축보다 구독이 싸다 (개발 인건비 고려하면 비교가 안 됨)
2. 단순 수집을 넘어 중복 그룹화·소스맵 변환·리플레이까지 필요하다면 도입 가치가 충분
3. 이미 잘 만들어진 도구가 있으면 쓰는 게 맞다

## 부록: 개인정보 이슈 체크리스트

도입 전 법무/보안 관점에서 챙길 것들.

- `sendDefaultPii: false` (권장): SDK 초기화에서 이 옵션을 끄면 IP, 쿠키, 사용자 ID 같은 개인식별정보(PII)를 자동 전송하지 않음
- IP 저장 차단: 대시보드 `Settings > Security & Privacy`에서 "Prevent Stored IP Addresses" 체크
- 개인정보 처리방침 업데이트: Sentry SaaS는 데이터가 미국 서버로 가므로 국외 이전 고지가 핵심
  - 수집 항목: 서비스 이용 기록, 접속 기기 정보(OS/브라우저), 에러 발생 정보(비식별 식별자)
  - 이전 국가: 미국 / 이전받는 자: Functional Software, Inc. (Sentry)
  - 이전 목적: 서비스 품질 개선·오류 모니터링 / 보유 기간: Sentry 보관 주기(기본 90일)
- 쿠키는 따로 쓰지 않고, 세션 리플레이는 sessionStorage 사용
- 국내법상 처리방침 고지만으로 운영 가능하지만, 보수적으로 가려면 "서비스 품질 개선을 위한 세션 분석" 항목으로 별도 안내하는 것이 좋다

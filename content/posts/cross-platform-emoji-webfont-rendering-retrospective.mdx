댓글의 🫶가 어떤 유저에겐 네모(☐)로 보인다는 신고가 왔다. 국기 이모지 🇨🇱는 그림 대신 `CL` 두 글자로 보인다고 했다. 지역도 제각각, 기기도 제각각이라 언뜻 랜덤처럼 보였고, 팀 내에선 "유튜브도 못 해주는 영역"이라며 해결 불가로 닫히기 직전이었다.

결론부터: 랜덤이 아니었고, 서버 문제도 아니었고, 해결 불가도 아니었다. 범인은 보는 사람의 OS에 깔린 이모지 폰트였고, 고치는 데 필요한 건 CSS 몇 줄과 웹폰트 하나였다. 이 기록의 핵심은 "해결 불가" 판정을 뒤집은 구분 하나 — 폰트를 설치하는 것과 서빙하는 것은 다르다 — 이다.

---

## 변수를 하나로 좁히기

이모지는 이미지가 아니라 글자다. 서버는 유니코드 문자열을 보냈을 뿐이고, 그걸 어떤 그림으로 그릴지는 받는 쪽 폰트가 정한다. 그러니 첫 질문은 "무엇이 다를 때 깨지는가"였다.

| 환경 | 엔진 | 이모지 폰트 | 🫶 |
|------|------|-----------|-----|
| Windows + Edge | Chromium | Segoe UI Emoji | ✗ 깨짐 |
| macOS + Chrome | Chromium | Apple Color Emoji | ✓ 정상 |

엔진이 같은데 OS만 다를 때 결과가 갈렸다. 이 교차 한 번으로 네트워크·CDN·렌더링 파이프라인 가설이 전부 떨어지고, 변수가 "OS 이모지 폰트" 하나로 좁혀진다.

다음은 깨진 문자가 정확히 뭔지였다. 신고 화면의 API 응답을 직접 받아 코드포인트를 뽑았다.

```
🫶  U+1FAF6   Emoji 14.0 (2021)   ← 깨짐
🥹  U+1F979   Emoji 14.0          ← 같은 조건에서 깨짐
🇨🇱  U+1F1E8 U+1F1F1   Emoji 1.0  ← Windows에서 "CL" 두 글자
🔥 ❤ 👏      Emoji 1.0~          ← 전부 정상
```

버전이 정확히 가른다. 이유는 두 갈래였다.

하나, Windows의 이모지 폰트는 OS 버전에 묶여 있다. Segoe UI Emoji의 Emoji 14.0 지원은 Windows 11 22H2(2022-09)부터다. 그 미만의 Windows 11과 모든 Windows 10에는 🫶 글리프가 아예 없다. Apple은 매년 따라가니 macOS/iOS에선 멀쩡했던 것. "랜덤"의 정체는 보는 사람의 OS 버전이었다.

둘, Windows는 국기를 정책적으로 안 그린다. 국기는 단일 문자가 아니라 Regional Indicator 두 글자 조합이고(🇨🇱 = `C`+`L`에 해당하는 특수문자 쌍), 폰트가 이 쌍을 국기 하나로 합성해줘야 한다. Microsoft는 정치적 부담 때문에 그 합성 글리프를 아예 안 넣는다. 그래서 OS 버전과 무관하게 Windows 전체에서 국기가 낱글자로 풀린다.

> 진단 팁: "이모지가 깨진다"는 신고에서 멈추지 말고 깨진 문자의 코드포인트와 Emoji 버전을 실측하라. 🔥는 되고 🫶만 안 된다면 그 자체가 폰트 버전 문제라는 물증이다.

## 죽을 뻔한 프로젝트를 살린 구분 하나

조사 중에 이런 정리가 있었다: "Noto Color Emoji 폰트를 설치하는 방법도 있으나, 크롬에서는 적용되지 않는 경우가 많다." 실제로 반쯤 맞는 말이라 여기서 "유저에게 폰트 설치를 시킬 수도 없고, 시켜도 안 먹히니 방법이 없다"로 결론 날 뻔했다.

그런데 이건 서로 다른 두 시나리오를 하나로 본 것이다.

| 시나리오 | 동작 |
|---|---|
| 유저가 자기 PC에 폰트를 설치 | ✗ Chrome은 이모지 렌더링에서 OS 내장 폴백을 우선하는 경향이 있어 잘 안 먹힌다 |
| 사이트가 `@font-face`로 폰트를 웹폰트 서빙 | ✓ 표준 CSS 폰트 매칭을 그대로 타므로 정상 동작한다 |

전자에 대한 관찰은 맞다. 하지만 우리가 할 일은 후자다. 유저 개입 없이 사이트 CSS만으로 해결된다. "해결 불가"와 "CSS 두 줄"의 차이가 이 구분 하나에 걸려 있었다.

## 이미지 치환은 왜 안 골랐나

twemoji처럼 텍스트에서 이모지 구간을 찾아 `<img>`로 바꿔치는 방식이 있다. OS 폰트와 완전히 무관해지니 언뜻 더 확실해 보이는데, 결정적 결함이 있다.

- `<input>`/`<textarea>` 안에서는 원리적으로 불가능하다. 유저가 댓글을 입력하는 동안엔 여전히 깨져 보인다. 반쪽 해결.
- 사용자 텍스트를 그리는 컴포넌트마다 래퍼를 기억해서 감싸야 한다. 하나 빠지면 조용히 회귀한다.
- ZWJ 조합·스킨톤·국기 쌍을 정규식으로 잘못 자르면 멀쩡한 글자를 깨뜨린다.
- `<img>` 노드라 텍스트 선택·복사가 나빠진다.

웹폰트는 이 문제가 전부 없다. 폰트 스택에 한 번 끼워 넣으면 CSS 상속으로 전역 자동 적용이라, 입력창 안이든 새로 만드는 컴포넌트든 따로 할 일이 없다.

```css
font-family: 'BodyFont', 'Apple Color Emoji', 'Noto Color Emoji', system-ui, sans-serif;
```

이 한 줄에서 순서가 설계의 전부다.

| 순서 | 역할 |
|------|------|
| 본문 폰트 | 일반 텍스트. 이모지 글리프가 없으니 이모지는 다음으로 폴백 |
| `'Apple Color Emoji'` | Apple 기기는 로컬 폰트로 매칭 → 웹폰트를 아예 안 받는다(0바이트) |
| `'Noto Color Emoji'` | Windows/Android/Linux의 이모지 담당 — 실제 수정 지점 |
| `system-ui, sans-serif` | 최후 폴백 |

`'Segoe UI Emoji'`는 일부러 뺐다. 그게 깨지는 원인인데 스택에 넣으면 Windows에서 Noto를 이겨버린다.

## 구현에서 아낀 것들

쓰는 만큼만 받게 — unicode-range 서브셋. 이모지 폰트 전체는 COLRv1 woff2 기준 ~1.85MB다. 대역별(국기/얼굴/사물/…)로 쪼개고 각 `@font-face`에 `unicode-range`를 걸면, 브라우저는 화면에 실제 등장한 코드포인트의 파일만 받는다.

```css
@font-face {
  font-family: 'Noto Color Emoji';
  src: url(./flags.woff2) format(woff2) tech(color-COLRv1);
  unicode-range: U+1F1E6-1F1FF;  /* 국기가 화면에 나올 때만 이 파일을 받는다 */
}
```

절약이 3단으로 걸린다. 이모지 없는 페이지 = 0바이트, Apple 기기 = 0바이트, 그 외 = 등장한 대역만. 실측해 보니 국기+얼굴 이모지가 있는 페이지에서 서브셋 11개 중 2개만 내려왔다.

프레임워크 폰트 로더의 preload 함정. Next.js `next/font/local`은 `preload` 기본값이 true다. 그대로 쓰면 이모지가 없는 페이지에서도, 심지어 이 폰트를 영원히 안 쓸 Apple 유저에게도 수 MB를 강제로 내려보낸다. `@font-face`(CSS import) 방식은 preload 태그 자체를 안 만들고, 어차피 unicode-range 분할을 하려면 폰트 로더로는 안 되니 CSS 방식이 답이다. 번들러가 콘텐츠 해시를 붙여주니 `immutable` 장기 캐싱도 따라온다. `public/`에 두는 방식은 캐시 정책이 빈약할 수 있어 확인이 필요하다 — 우리 환경은 max-age=5였다.

검증 환경의 역설. CI/서버용 Linux엔 보통 이모지 폰트가 없다. 평소엔 골칫거리인데 이 작업에선 최고의 테스트베드가 된다 — 웹폰트가 동작해야만 컬러 이모지가 보이는 환경이라 적용 전/후가 극명하게 갈린다. 헤드리스 브라우저로 이모지를 주입해 스크린샷과 네트워크 로그(어느 서브셋이 로드됐나)를 찍으면 기계적으로 판정된다.

국기는 전수로. RGI 국기 시퀀스는 258개다. 몇 개 찍어보는 걸로는 모자라서 전체 목록을 생성해 붙여넣었다. 별도 인코딩인 tag sequence 3종(잉글랜드/스코틀랜드/웨일스)과 ZWJ 깃발(🏳️‍🌈 🏳️‍⚧️ 🏴‍☠️)도 따로 챙겨야 한다. 함정 하나: 폐기된 ISO 코드(AN, YU, SU 같은 것 22개)는 어떤 폰트에도 글리프가 없어서 목록에 섞이면 "깨졌다"는 오탐을 만든다. 미리 걸러낼 것.

## 밟은 함정들

① 국기가 코드 글자 깃발로 나오는 폰트가 있다. 폰트 견본 사이트에서 weight가 있는 흑백 Noto Emoji를 열었더니 국기 자리에 전부 "펄럭이는 깃발 테두리 + 국가코드 두 글자"가 그려져 있었다. 처음엔 웃겼는데, 알고 보니 모노크롬 버전은 2022년에 국기를 정책적으로 들어낸 것이고 컬러 버전과는 다른 폰트였다. 웃고 넘어갈 일이 아닌 게 — 배포할 그 파일이 이 모양이면 국기 없는 폰트를 서빙하는 사고가 된다. 파일을 실제로 렌더링해서 국기가 진짜 그림으로 나오는지 확인하고 갔다.

② 같은 폰트에도 컬러 포맷이 여럿이다. COLRv1 / OpenType-SVG / 비트맵(CBDT). OT-SVG 빌드는 Chrome/Edge가 지원하지 않는다 — 정작 고쳐야 할 Windows에서 조용히 실패한다. COLRv1인지 확인하고 받아야 한다.

③ `tech()` 힌트는 모르는 브라우저에서 src를 통째로 무효화한다. `src: url(...) format(woff2) tech(color-COLRv1)`에서 `tech()`를 파싱 못 하는 구형 브라우저는 힌트만 무시하는 게 아니라 그 src 전체를 버린다. 다만 그 구간(대략 2022년 이전)은 어차피 COLRv1을 못 그리니 "원래 깨졌고 계속 깨짐"이지 회귀는 아니다. 수용 가능한지만 판단하면 된다.

④ 서브셋 패키지는 갱신이 멈출 수 있다. 미리 잘라둔 서브셋을 npm으로 배포하는 패키지로 시작했는데, 나중에 보니 저자가 손을 놓아 폰트가 2년 전 유니코드 버전에 멈춰 있었다. 최신 이모지(🫩 같은 것)는 이미 폰의 키보드에 깔렸는데 웹폰트엔 글리프가 없는 상태. 그리고 이건 어떤 방식으로도 자동으로는 안 된다 — 폰트는 정적 파일이라 새 글리프가 담긴 릴리즈로 갈아끼우는 수밖에 없다. 장기적으로는 원본 릴리즈를 직접 서브셋하는 스크립트를 레포에 두고 매년 유니코드 릴리즈 후 한 번 돌리는 운영이 낫다. 신규 이모지는 발표 후 유저 기기에 퍼지기까지 반년 이상 걸리니 느슨하게 따라가도 된다.

⑤ 부분 해결책과의 중복 정리. 국기 문제만 먼저 국기 대역 전용 폴리필(수십 KB 웹폰트 주입)로 막아둔 상태였다. 전체 이모지 웹폰트가 들어오면 이게 중복이 되는데, 제거는 반드시 새 폰트의 국기 커버리지를 실측 확인한 뒤 같은 배포에서 해야 한다. 순서를 틀리면 국기가 다시 깨지는 공백이 생긴다. 부수 효과로 국기만 그림체가 다르던 문제도 같이 사라졌다.

## 요약

1. 이모지는 글자다. 깨짐의 범인은 서버가 아니라 보는 쪽 폰트다.
2. 같은 엔진·다른 OS 교차 한 번이면 원인이 좁혀진다. 코드포인트 실측이 물증을 만든다.
3. "폰트 설치는 안 먹힌다"와 "웹폰트 서빙은 먹힌다"는 다른 얘기다. 이 구분이 해결 가능/불가를 갈랐다.
4. 이미지 치환은 입력창을 못 고친다. 웹폰트는 상속으로 전역 적용된다.
5. 스택 순서로 Apple은 0바이트, unicode-range로 나머지도 쓰는 만큼만.
6. 함정은 전부 "파일이 생각과 다른" 형태였다 — 모노크롬, OT-SVG, 낡은 패키지. 배포할 파일 그 자체로 검증하라.

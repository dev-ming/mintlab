웹 서비스에 React Native 앱을 추가하기로 하면서, TanStack Query 훅(데이터 로직)을 웹 앱에서 모노레포 패키지로 분리했다. "좋아요 버튼 하나"를 표본으로 왜 분리했는지, 어떤 패턴으로 분리했는지, 어떤 함정이 있는지 정리.

---

## 왜 분리하나 — 화면은 다시 만들어도, 데이터 규칙은 다시 만들지 않는다

"좋아요를 누르면 → 요청을 보내고 → 어떤 캐시를 갱신하고 → 실패하면 되돌린다" 같은 규칙은 웹과 앱에서 완전히 동일해야 한다. 이 로직이 웹 컴포넌트 안에 박혀 있으면:

- RN에서 처음부터 다시 짜야 하고
- 두 벌이 되는 순간부터 서서히 어긋난다 (한쪽만 고치는 사고)

그래서 데이터 로직만 `packages/queries` 같은 공용 패키지로 꺼낸다. 인증/토큰 갱신 로직(`api-client`), i18n 카탈로그도 같은 원칙으로 분리 대상이다.

```
apps/web  (화면·플랫폼 구현)     packages/queries  (공용 규칙)     apps/mobile (예정)
─────────────────────────      ─────────────────────────       ─────────────────
카드 UI · 낙관적 상태 · 토스트  ⇄  요청 순서 · 성공/실패 처리      ⇄  네이티브 UI
fetch 함수 (웹 HTTP 클라이언트)     캐시 무효화 · 쿼리 키 레지스트리     RN용 fetch 함수
sessionStorage · router 등          (브라우저도 RN도 모름)              AsyncStorage 등
```

가운데는 브라우저도 RN도 모른다. 양쪽이 자기 재료를 주입하고, 결과를 콜백으로 돌려받는다.

---

## 전제 지식: TanStack Query 4가지

1. Query vs Mutation — Query는 서버 데이터를 읽어 캐시에 보관(`useQuery`), Mutation은 서버 상태를 바꾸는 요청 한 번(`useMutation`). 좋아요는 Mutation을 쏘고, 그 결과로 여러 Query 캐시가 낡는다.
2. Mutation 생명주기 — `mutate()` → `onMutate`(요청 직전, 낙관적 업데이트 자리) → `mutationFn`(실제 요청) → `onSuccess`/`onError` → `onSettled`(성공이든 실패든 무조건). 정리 작업은 onSettled가 자리다.
3. queryKey는 배열, 무효화는 프리픽스 매칭 — `invalidateQueries({ queryKey: ['home'] })`는 `['home']`, `['home', 'en']`은 잡지만 `['home-extra-feed']`는 못 잡는다. 앞부분이 달라지면 남남이다.
4. 낙관적 업데이트 — 응답을 기다리지 않고 UI를 먼저 바꾼다. 대가: 실패하면 되돌려야 하고, 서버 확정값 도착 전에 걷어내면 옛 값이 보인다.

## 패턴 A. 의존성 주입 — 훅이 fetcher를 import하지 않는다

패키지 훅이 웹의 fetch 함수를 import하는 순간 (토큰 헤더, sessionStorage, 401 리프레시에 묶여서) RN에서 못 쓴다. 그래서 함수를 인자로 받는다.

```ts
// packages/queries — 훅은 "요청하는 방법"을 모른다
export interface LikeInListDeps {
  like: (id: string) => Promise<unknown>;   // 웹이든 RN이든 자기 것을 주입
  unlike: (id: string) => Promise<void>;
}

export function useLikeInList(params, deps: LikeInListDeps, callbacks) { ... }
```

응답 타입이 `unknown`인 것도 같은 이유 — 패키지는 응답 모양을 해석하지 않고 콜백으로 통과만 시키고, 구체 타입 캐스팅은 화면 쪽 몫이다.

판별법: 패키지 파일에 앱 경로 import, `window`, `sessionStorage`가 보이면 잘못 들어온 것. 플랫폼 재료는 전부 매개변수로.

## 패턴 B. 역할 분리 — 낙관적 UI는 화면이, 요청·무효화는 훅이

상세 화면용 훅은 자기 쿼리 키를 알아서 캐시를 직접 낙관적으로 고칠 수 있다. 그런데 목록 카드는 여러 목록(탭, 홈 피드, 확장 목록…)에 꽂혀서 자기가 어느 캐시에 있는지 모른다. 그래서 역할을 쪼갠다:

| 누가 | 무엇을 | 어떻게 |
| --- | --- | --- |
| 화면 (카드) | 낙관적 표시 | 로컬 state로 하트·카운트를 먼저 뒤집어 보여줌 |
| 훅 (패키지) | 요청 + 무효화 | mutation 실행, 성공·실패 무관하게 관련 쿼리 전부 invalidate |
| 콜백 | 둘 사이 신호 | `onOptimistic`(지금 뒤집어라) / `onReset`(이제 풀어라) / `onResult`(응답 전달) |

핵심 타이밍: override 해제(`onReset`)는 `onSettled`에서, invalidate를 `await`한 다음이다.

- onSuccess에서 풀면 → 실패 시 안 풀려서 낙관값에 영영 고정
- invalidate 완료 전에 풀면 → 서버 새 데이터가 오기 전 옛 캐시가 한 프레임 그려져 깜빡임

## 패턴 C. 쿼리 키 중앙 레지스트리

액션 하나가 여러 도메인의 캐시에 영향을 주므로(좋아요 → 홈 피드·목록·상세), 키를 한 파일(`keys.ts`)에 모아 프리픽스 관계를 관리한다.

```ts
home: {
  all:  () => ['home'],               // 프리픽스 — 이걸 invalidate하면
  feed: (locale) => ['home', locale], // 이것도 같이 무효화된다
  extraFeed: () => ['home-extra'],    // ⚠ 프리픽스 밖! 따로 불러야 한다
}
```

## 실전 사고: "좋아요가 되돌아가요"

이 구조의 대표적 약점을 실제로 겪었다. 증상: 홈의 확장 목록에서 좋아요를 누르면 하트가 채워졌다가 다시 비워진다. 서버에는 정상 반영됐는데.

원인: 확장 목록의 쿼리 키가 기존 프리픽스 밖에 있었는데 훅의 무효화 목록에서 빠져 있었다. 흐름으로 보면 —

1. 클릭 → 낙관적 override로 하트 채워짐
2. 요청 성공, 무효화 실행 — 그런데 이 목록의 캐시는 무효화 대상이 아님
3. `onReset`으로 override 해제 → 갱신 안 된 옛 캐시가 다시 그려짐 → 하트가 되돌아가 보임

교훈: 무효화 목록이 곧 정합성이다. 새 화면에 공용 카드를 꽂을 때는 그 화면의 쿼리 키가 (1) 기존 프리픽스 아래인지, (2) 밖이라면 훅의 무효화 목록에 추가했는지를 반드시 확인해야 한다. "서버엔 반영됐는데 화면만 되돌아간다"가 시그니처 증상이다.

## 운영 규칙

- 빌드 파이프라인: 패키지는 tsc로 dist를 만들고 앱이 산출물을 쓴다면, 패키지 수정 후 빌드를 잊으면 "고쳤는데 그대로"가 된다.
- 시그니처는 하위 호환으로: 소비자가 지금은 웹뿐이어도 구조상 곧 둘이 된다. 콜백 추가는 옵셔널 파라미터로.
- 경계 감시: 코드리뷰에서 패키지 쪽 diff에 플랫폼 import가 섞이는지가 1순위 체크포인트.

## 셀프 체크

1. RN에서 이 훅을 그대로 쓰려면? → RN용 fetcher 한 쌍 + 화면 쪽 구현(낙관적 상태·콜백)만. 훅과 키 레지스트리는 무수정.
2. onReset이 onSettled + await invalidate 뒤인 이유? → 실패해도 풀어야 하고, 새 데이터 도착 후 풀어야 깜빡임이 없다.
3. `invalidate(['home'])`이 `['home-extra']`를 못 잡는 이유? → 프리픽스 매칭. 배열 앞부분이 다르면 남남.
4. 패키지에서 sessionStorage를 읽으면 안 되는 이유? → 플랫폼 결합. 주입이 유일한 통로.

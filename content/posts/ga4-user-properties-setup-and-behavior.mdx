이벤트만 쌓으면 "무엇이 일어났는지"는 알지만 "어떤 사람이 그랬는지"는 못 나눈다. GA4의 사용자 속성으로 그 축을 만드는 방법과, 겉보기와 다르게 동작하는 지점들을 정리한 글.

---

## 0. 문제 — 이벤트만으로는 사람을 나눌 수 없다

이벤트 트래킹을 붙이면 이런 질문에는 답할 수 있다.

- 어떤 버튼이 많이 눌렸나
- 어느 화면에서 이탈하나

그런데 실제로 듣는 질문은 대개 이쪽이다.

- 20대 여성의 참여율이 다른 집단보다 높은가
- 가입할 때 특정 관심사를 고른 사람이 더 오래 남는가

이걸 이벤트 파라미터로 해결하려면 모든 이벤트에 성별·연령대를 매번 실어야 한다. 중복이고, 빠뜨리는 이벤트가 반드시 생긴다. 사용자 속성은 이 축을 한 번 선언해두고 모든 이벤트에 자동으로 따라붙게 하는 장치다.

---

## 1. 이벤트 파라미터 vs 사용자 속성

| | 이벤트 파라미터 | 사용자 속성 |
| --- | --- | --- |
| 범위 | 그 이벤트 하나 | 그 사용자 전체 |
| 성격 | 그 순간의 사실 | 사람의 속성 |
| 이력 | 이벤트마다 남는다 | 최신값만 남는다 |
| 예 | `button_id`, `amount` | `gender`, `age_band` |

판단 기준은 하나다. "시점이 중요한가, 사람이 중요한가."

"결제 금액"은 시점의 사실이니 파라미터다. "성별"은 사람의 속성이니 사용자 속성이다. 헷갈리는 건 "가입 시 고른 관심사" 같은 것 — 사람의 속성처럼 보이지만 *시점*이 의미를 가진다면 파라미터로도 함께 남겨야 한다(5절 참고).

---

## 2. 설정 방법

`gtag`로는 이렇게 넘긴다.

```ts
gtag('set', 'user_properties', {
  gender: 'female',
  age_band: '20_24',
  country: 'PE',
});
```

래퍼를 하나 두면 값 제한(4절)을 한곳에서 처리할 수 있다.

```ts
// lib/analytics.ts
const USER_PROPERTY_MAX_LENGTH = 36;

export function setUserProperties(props: Record<string, string | number | boolean>): void {
  const clamped: typeof props = {};
  for (const [key, value] of Object.entries(props)) {
    clamped[key] = typeof value === 'string' ? value.slice(0, USER_PROPERTY_MAX_LENGTH) : value;
  }
  gtag('set', 'user_properties', clamped);
}
```

길이 초과분은 GA가 알아서 자르는데, 어디서 잘렸는지 모르게 되므로 미리 자르는 편이 낫다.

---

## 3. 핵심 — `set`은 전송하지 않는다

가장 많이 오해하는 지점이다. `gtag('set', ...)`은 네트워크 요청을 보내지 않는다. 값을 페이지 안 상태에 담아두기만 한다.

```
gtag('set', 'user_properties', { gender: 'female' })   ← 요청 없음
        ↓
gtag('event', 'sign_up', { ... })                      ← 이때 함께 전송
        ↓  수집 요청에 up.gender=female 형태로 실려 나간다
Google 도달 = 실제 저장 시점
```

여기서 따라오는 결론 두 개.

하나, `set` 뒤에 이벤트가 없으면 값은 영영 안 나간다. 그래서 값을 설정하는 지점은 이벤트 바로 앞이 가장 안전하다.

```ts
setUserProperties({ ...selections });        // 먼저
trackEvent('onboarding_complete');          // 바로 뒤 — 여기 실려 나간다
```

둘, 비동기로 값을 만들면 타이밍을 못 고른다. 프로필을 조회해서 속성을 채우는 경우, 조회가 끝난 시점엔 이미 첫 `page_view`가 지나가 있다. 그러면 그 다음 이벤트부터 붙는다. 버그는 아니지만 "로그인 직후 첫 이벤트에 붙는다"고 기대하면 어긋난다.

---

## 4. 어디에 어떻게 저장되나

값은 식별자에 붙어서 Google 쪽에 저장된다. 우리 서버에는 아무것도 저장되지 않는다.

| 식별자 | 정체 |
| --- | --- |
| `client_id` | 분석 쿠키의 브라우저·기기 단위 난수 |
| `user_id` | 앱이 직접 넣는 내부 식별자 (`gtag('set', { user_id })`) |

여기서 절대 넣지 말아야 할 것이 정해진다. 이메일·이름·전화번호 같은 직접 식별 정보는 분석 도구 약관 위반이다. `user_id`에도 내부 UUID처럼 그 자체로는 사람을 특정할 수 없는 값을 쓴다.

그래서 원본 데이터를 그대로 넣는 대신 이렇게 변환한다.

| 원본 | 보내는 값 |
| --- | --- |
| 생년월일 `1998-03-15` | `age_band: '25_29'` |
| 선호 항목 목록 | `fav_count: 5` |
| 이름·이메일 | 안 보냄 |

브라우저에는 값이 남지 않는다. `gtag`가 메모리에만 들고 있어서 새로고침하면 사라진다. 반면 Google 쪽에는 그 사용자에게 붙어 유지되므로, 매 세션 다시 보내지 않아도 사용자 범위 리포트는 마지막 값으로 집계된다.

---

## 5. 덮어쓰기 — 이력이 남지 않는다

사용자 속성은 최신값 하나만 유지된다. 값을 바꾸면 그 사용자의 과거 데이터도 새 값 기준으로 보인다.

- 성별·연령대처럼 잘 안 바뀌는 값 → 문제없다
- "가입 시 고른 관심사"는 함정이다 — 나중에 관심사를 바꾸면 가입 당시 분석이 오염된다

시점이 의미를 갖는 값은 사용자 속성과 이벤트 파라미터 양쪽에 남겨야 한다. 사용자 속성은 "지금 이 사람은 어떤 사람인가"(세그먼트용), 이벤트 파라미터는 "그때 무엇을 골랐나"(코호트용)로 역할이 다르다.

---

## 6. 리포트에 나오게 하려면 — 등록이 필요하다

값을 보내는 것과 리포트에서 보이는 것은 별개다. 코드로 아무리 보내도, 관리자에서 맞춤 측정기준(custom dimension) 으로 등록하지 않으면 리포트·탐색·세그먼트 어디에도 나타나지 않는다.

```
관리 → 데이터 표시 → 맞춤 정의 → 맞춤 측정기준 → 측정기준 만들기
  · 범위 = 사용자        ← 기본값이 "이벤트"라 반드시 바꾼다
  · 사용자 속성 = 코드에서 보낸 이름과 정확히 일치
```

여기서 두 가지가 사람을 잡는다.

소급 적용이 안 된다. 등록 시점 이후 수집분만 보인다. 배포하고 한 달 뒤에 등록하면 그 한 달은 영영 못 본다 → 등록을 배포 전이나 직후에 해야 한다.

한도가 있다. 사용자 범위 맞춤 측정기준은 속성당 25개다. 불리언으로 잘게 쪼개면 금방 찬다. 쓰기 전에 예산을 세워두는 게 좋다.

표준 리포트 반영에는 하루 이틀 걸린다. 값이 제대로 붙는지 즉시 보려면 DebugView를 쓴다(10절).

---

## 7. 제약 안에서 값 설계하기

| 제약 | 값 |
| --- | --- |
| 속성 이름 | 24자 |
| 속성 값 | 36자 |
| 사용자 속성 개수 | 25개 |

값 36자가 설계를 크게 흔든다. 목록을 문자열로 담을 수 없다.

```ts
// ✗ 넘친다 — 항목이 늘면 조용히 잘린다
interests: 'kpop,kbeauty,kdrama,kfood,kfashion,kmovies'   // 42자

// ✓ 옵션마다 불리언으로 펼친다
interest_kpop: true,
interest_kbeauty: false,
// ...
```

불리언 전개의 장점은 세그먼트를 그대로 만들 수 있다는 것이고, 단점은 25개 한도를 빨리 쓴다는 것이다. 항목이 많으면 개수 + 대표값 조합도 방법이다.

```ts
fav_count: 5,
fav_top: 'BTS',        // 36자 안에 들어가는 단일 값
```

이걸 도우는 헬퍼는 이렇게 생긴다.

```ts
export function toSelectionProperties(
  prefix: string,
  allKeys: readonly string[],
  selectedKeys: readonly string[],
): Record<string, boolean> {
  const selected = new Set(selectedKeys);
  return Object.fromEntries(allKeys.map((key) => [`${prefix}_${key}`, selected.has(key)]));
}
```

`allKeys`를 넘기는 이유는 선택하지 않은 항목도 `false`로 명시하기 위해서다. 아예 안 보내면 "선택 안 함"과 "데이터 없음"이 구분되지 않는다.

---

## 8. 언제 설정할 것인가

Google 쪽에 값이 유지되니 이론상 한 번이면 충분하다. 그런데 실제로는 재설정이 필요하고, 이유는 셋이다.

1. 값이 바뀐다 — 프로필을 수정하거나 선택을 다시 한 경우
2. 아직 한 번도 안 보낸 사용자 — 기능 배포 전에 가입한 사람들
3. 기기·브라우저가 바뀐다 — 새 기기의 첫 이벤트에는 값이 없다

그래서 실용적인 규칙은 "세션당 1회, 서버 값과 다를 때만" 이다.

```ts
const SESSION_KEY = 'user_props_synced';

export async function syncUserProperties(serverValue: string | undefined): Promise<void> {
  if (typeof window === 'undefined') return;
  if (serverValue === undefined) return;                       // 아직 지원 안 하는 응답
  if (sessionStorage.getItem(SESSION_KEY)) return;             // 세션당 1회
  if (serverValue === currentValue()) return;                  // 다를 때만
  sessionStorage.setItem(SESSION_KEY, '1');                    // 병렬 호출 선점
  try {
    setUserProperties({ ... });
  } catch {
    sessionStorage.removeItem(SESSION_KEY);                    // 다음 세션에 재시도
  }
}
```

두 가지 디테일이 있다.

플래그를 작업 전에 세운다. 로그인 확인 함수가 여러 화면에서 병렬로 불리는 구조라면, 나중에 세우면 중복 실행된다.

실패 시 플래그를 되돌린다. 안 되돌리면 그 세션 내내 재시도가 막힌다.

로그아웃 시 이 플래그를 지우는 것도 잊지 말아야 한다. 계정이 바뀌었는데 이전 사용자의 속성이 그대로 남으면 데이터가 섞인다.

## 9. 함정 모음

`set` 뒤에 이벤트가 없다 → 값이 전송되지 않는다. 3절.

동의 전에 보낸다 → 동의 관리(Consent Mode 등)를 쓰면 동의 전에는 전송이 막힌다. 정상 동작이지만, 테스트할 때 "왜 안 나가지"로 헤매기 쉽다. 동의를 먼저 켜고 확인한다.

연령대 계산의 시간대 버그 — 이건 직접 밟았다.

```ts
// ✗ 'YYYY-MM-DD'는 UTC 자정으로 파싱되는데 getFullYear 등은 로컬 기준이다
//   → UTC보다 뒤인 지역(미주)에서 나이가 하루 밀린다
const dob = new Date(dateOfBirth);
let age = now.getFullYear() - dob.getFullYear();

// ✓ 문자열을 직접 쪼개 시간대를 아예 개입시키지 않는다
const [year, month, day] = dateOfBirth.slice(0, 10).split('-').map(Number);
let age = now.getFullYear() - year;
const monthDiff = now.getMonth() + 1 - month;
if (monthDiff < 0 || (monthDiff === 0 && now.getDate() < day)) age--;
```

경계값(생일 당일, 생일 하루 전, 하한 미달)은 반드시 확인해야 한다. 글로벌 서비스면 시간대까지.

모듈 순환 참조 — 속성 모듈이 프로필 조회를 부르고, 조회가 API 클라이언트를, 클라이언트가 인증 모듈을 부르는데, 인증 모듈이 다시 속성 모듈의 상수를 참조하면 사이클이 된다. ESM은 사이클을 허용하지만 모듈 초기화 시점에 `undefined`가 될 수 있다. 공유 상수는 의존 그래프의 가장 아래(인증·설정 모듈)에 둔다.

불필요한 조회 추가 — 속성을 채우려고 프로필을 새로 조회하기 전에, 로그인 응답에 그 값이 이미 있는지 확인하는 게 좋다. 있으면 그걸 넘겨받아 요청 하나를 줄일 수 있다.

## 10. 검증

표준 리포트는 하루 이틀 걸리므로 DebugView로 즉시 확인한다.

1. 디버그 모드를 켠다 (디버그용 확장 프로그램 또는 SDK 디버그 옵션)
2. 관리자의 DebugView에서 실시간 이벤트 스트림을 본다
3. 이벤트를 열어 사용자 속성이 붙었는지 확인한다

여기서 안 보이면 순서 문제(3절)거나 동의 문제(9절)다. 보이는데 리포트에 없으면 등록 문제(6절)다. 이 세 갈래로 나눠 보면 원인이 빨리 좁혀진다.

## 11. 체크리스트

- [ ] 이 값이 "사람의 속성"인가 "시점의 사실"인가 — 후자면 이벤트 파라미터로
- [ ] 시점이 의미 있으면 양쪽에 남겼는가 (5절)
- [ ] 직접 식별 정보를 빼고 변환했는가 (생년월일 → 연령대 등)
- [ ] 값 36자 / 이름 24자 / 총 25개 안에 들어오는가
- [ ] 선택 안 한 항목도 `false`로 명시했는가
- [ ] `set` 뒤에 이벤트가 실제로 발생하는가
- [ ] 관리자에 사용자 범위로 등록했는가 (배포 전/직후에)
- [ ] 세션당 1회 + 값이 다를 때만 보내는가
- [ ] 로그아웃 시 동기화 플래그를 지우는가
- [ ] 연령대 경계값을 테스트했는가
- [ ] 수집 항목이 개인정보처리방침에 반영되어 있는가

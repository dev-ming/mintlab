## 배경

어느 날 세션 상태를 보니 기본 모델이 Fable로 잡혀 있었다. 한 번 `/model`로 골라본 게 그대로 저장돼서, 그 뒤로 모든 세션이 최상위 모델로 돌고 있었던 것이다. 파일 이름 바꾸고 lint 돌리는 턴까지 전부.

실무에서 하루 종일 Claude Code를 쓰면 작업의 성격이 꽤 갈린다.

- 대부분의 턴은 평범하다. 티켓 받아서 조사하고, 고치고, 타입체크 돌리고, 커밋 메시지 쓰는 일.
- 가끔 막힌다. 원인이 안 잡히는 버그, 여러 패키지에 걸친 리팩토링, 설계 판단이 필요한 순간.
- 보안이 걸린 변경은 따로 있다. 인증, 결제, 권한처럼 놓치면 비싼 곳.

이 세 가지에 같은 모델을 쓰는 건 낭비다. "평소엔 Opus, 막히거나 보안 리뷰가 필요할 때만 Fable"이 비용과 한도 면에서 제일 합리적인데, 이게 Claude Code에서 실제로 되는지 확인하고 적용한 기록이다.

결론부터 말하면 된다. 그것도 세 층위에서 따로 조절할 수 있다.

---

## 결과 먼저 보기

| 층위 | 모델 | 어떻게 |
|---|---|---|
| 메인 세션 기본값 | Opus | `/model opus` 한 번 (설정에 저장됨) |
| 막힌 구간 | Fable | `/model fable` → 해결 후 `/model opus` 복귀 |
| 구현 서브에이전트 | Opus | 에이전트 정의 파일 `model: opus` |
| 리뷰 서브에이전트 | Opus | 에이전트 정의 파일 `model: opus` |
| 보안 리뷰 | Fable | 리뷰 에이전트를 호출할 때만 `model: fable` 지정 |
| QA 서브에이전트 | Haiku | 에이전트 정의 파일 `model: haiku` |

핵심은 정의 파일에 박는 건 평소 값, 호출 시점에 올리는 건 예외 값이라는 분리다.

## 1. 단가 감각부터

API 기준 단가(1M 토큰당, 입력 / 출력)다. 구독 플랜은 토큰 단가가 아니라 한도로 묶이지만, 어느 모델이 몇 배 무거운지 감을 잡는 데는 이 표가 제일 빠르다.

| 모델 | 입력 | 출력 | 배수(Opus 기준) |
|---|---|---|---|
| Fable 5.1 | $10 | $50 | 2.5× |
| Opus 5.5 | $4 | $20 | 1× |
| Sonnet 5.5 | $2 | $10 | 0.5× |
| Haiku 5.5 | $0.10 | $0.50 | 0.025× |

두 가지가 눈에 들어온다.

- Fable은 Opus의 2.5배다. 그리고 플랜과 좌석 등급에 따라 플랜 포함 한도가 아니라 사용량 크레딧으로 따로 과금될 수 있다. 그 경우 `/model` 피커의 Fable 행에 "Requires usage credits"라고 표시된다. 비대화 모드(`-p`)에서는 묻지 않고 과금되니 스크립트에서 Fable을 쓸 때는 특히 조심.
- Haiku는 거의 공짜다. typecheck·lint·테스트를 돌리고 결과를 보고하는 일에 Opus를 쓸 이유가 없다.

## 2. 메인 세션 기본 모델 정하기

```
/model opus
```

피커에서 Enter를 누르면 사용자 설정 파일의 `model` 필드에 저장돼 다음 세션부터 기본값이 된다. `s`를 누르면 이번 세션만 바꾸고 저장은 하지 않는다.

설정 파일을 직접 고쳐도 된다.

```json
// ~/.claude/settings.json
{
  "model": "claude-opus-5-5"
}
```

단, 파일의 `model` 값은 세션 시작 시에만 읽는다. 세션 중에 바꾸려면 `/model`을 써야 한다.

우선순위는 이렇다(높은 순).

1. 세션 중 `/model`
2. 시작 시 `claude --model`
3. 환경변수 `ANTHROPIC_MODEL`
4. 설정 파일의 `model` (프로젝트 로컬 > 프로젝트 공유 > 사용자)
5. `ANTHROPIC_DEFAULT_MODEL` (어떤 파일도 `model`을 안 정했을 때만)

팀 공유 설정에 모델이 박혀 있는데 나만 다르게 쓰고 싶으면 `.claude/settings.local.json`에 두면 된다.

## 3. 막힐 때만 Fable로 올리기

```
/model fable
```

즉시 전환된다. 대화 이력은 그대로 유지되고, 다음 턴부터 Fable이 이어받는다. 풀리면 `/model opus`로 돌아온다.

여기서 하나 알아둘 게 있다. 프롬프트 캐시는 모델별로 따로 있다. 그래서 전환 직후 첫 턴은 지금까지의 대화 이력 전체를 캐시 없이 다시 처리한다. 그 한 턴만 느리고 비싸다. 캐시가 아직 살아 있을 때 전환하면 확인 창이 뜨는 것도 이 때문이다.

실전 요령은 왔다갔다하지 말고 몰아서다. 막힌 지점을 Fable로 올렸으면 그 문제를 끝까지 풀고 내려온다. 턴마다 모델을 바꾸면 매번 캐시 미스가 나서 오히려 손해다.

한도 메시지도 두 종류라는 걸 알아두면 좋다.

- "Opus 한도에 도달했습니다" 같은 모델별 한도는 다른 계열로 `/model` 전환하면 계속 작업할 수 있다.
- 주간·세션 공통 한도는 모든 모델에 걸리므로 모델 전환으로 우회되지 않는다.

## 4. 서브에이전트마다 모델 고정하기

메인 세션이 PM을 맡고 구현·리뷰·QA는 서브에이전트가 하는 구조라면, 각 에이전트 정의 파일 프론트매터에 모델을 명시한다. 이걸 비워두면 `inherit`처럼 메인 세션 모델을 따라가서, 메인을 Fable로 올린 순간 서브에이전트까지 전부 Fable이 된다.

```markdown
---
name: app-task
description: 일감을 받아 조사 → 수정 → typecheck까지. 커밋·푸시는 하지 않는다.
model: opus
---
```

```markdown
---
name: app-review
description: 변경분을 독립적으로 리뷰해 must-fix / should-fix / nit로 판정.
model: opus
---
```

```markdown
---
name: app-qa
description: 변경분에 typecheck / lint / test를 독립 실행하고 PASS/FAIL만 보고.
model: haiku
---
```

`model:`에 들어갈 수 있는 값은 별칭(`sonnet` / `opus` / `haiku` / `fable`), 전체 모델 ID(`claude-opus-5-5` 등), 그리고 `inherit`다.

서브에이전트 모델이 결정되는 순서는 이렇다.

1. 호출할 때 넘긴 `model` 파라미터 (별칭만 가능)
2. 정의 파일의 `model:` 프론트매터
3. 환경변수 `CLAUDE_CODE_SUBAGENT_MODEL`
4. 메인 세션 모델

### 왜 이렇게 배분했나

- 구현은 Opus. 구현 품질이 재작업 횟수를 좌우한다. 여기서 아끼면 리뷰에서 반려되고 다시 구현하는 루프가 돌아서 결국 더 쓴다.
- 리뷰는 구현자와 같은 급 이상. 구현자보다 약한 모델이 리뷰하면 리뷰 단계가 통과 의례가 된다. 같은 Opus라도 "다른 세션, 다른 프롬프트, 다른 관점"이라 독립성은 확보된다.
- QA는 Haiku. 명령 실행하고 결과 읽고 보고하는 일이다. 판단력보다 실행이 주 업무라 가장 싼 모델로 충분하다. 다만 "실패 로그를 통째로 붙이지 말고 요약해라" 같은 토큰 규칙은 정의 파일에 같이 박아둔다.

## 5. 보안 리뷰만 Fable로 — 정의 파일은 건드리지 않는다

리뷰 에이전트를 아예 `model: fable`로 고정할 수도 있다. 하지만 그러면 모든 티켓의 리뷰 비용이 2.5배가 된다. 대부분의 변경은 UI 문구 수정이나 쿼리 하나 추가라서 그럴 필요가 없다.

대신 호출 시점에만 올린다. 메인 세션이 리뷰 에이전트를 띄울 때 `model: fable`을 넘기면, 그 호출 한 번만 Fable로 돈다. 정의 파일의 `model: opus`는 그대로다.

"이 변경은 인증 토큰 갱신 로직이니까 리뷰는 fable로" 한 마디면 된다. 조건을 미리 정해두면 더 편하다. 우리 경우는 인증·결제·권한·세션 저장소를 건드리는 변경이 기준이다.

## 6. 5개월 전 결정을 다시 꺼낸 이유

사실 서브에이전트 모델은 이미 고정돼 있었다. 구현·리뷰는 Sonnet, QA는 Haiku. 2026년 6월에 "비용 절감" 명목으로 정한 값이었고, README에도 그렇게 적혀 있었다.

그 사이 라인업이 바뀌었다. 당시 `opus`는 Opus 4.x, `sonnet`은 Sonnet 4.6이었고 둘의 단가 차이가 지금보다 컸다. 지금 `opus` 별칭은 Opus 5.5, `sonnet`은 Sonnet 5.5로 해석되고 격차는 딱 2배다. 그리고 그 위에 Fable이라는 한 단계가 더 생겼다.

"Opus는 비싸다"는 전제가 완전히 틀린 건 아니지만, 비교 대상이 바뀌면 결론도 바뀐다. Sonnet으로 아껴서 반려 루프를 한 번 더 도는 것과, Opus로 한 번에 통과하는 것 중 어느 쪽이 싼지는 2배 격차에서는 후자 쪽이 유리하다고 봤다.

여기서 얻은 교훈 하나. 모델 정책에는 날짜와 근거를 같이 적어둔다. "비용 절감을 위해 sonnet"이라고만 써두면 나중에 왜 그랬는지 모른다. "2026-06 기준 Opus 4.x 대비 단가 차이 때문에 sonnet, 라인업 바뀌면 재검토"라고 써두면 다음 사람이(대개 미래의 나다) 판단할 수 있다.

## 주의사항

- 별칭은 환경마다 다르게 풀린다. `opus`는 Anthropic API에서 Opus 5.5지만 일부 서드파티 플랫폼에서는 이전 버전으로 풀린다. `fable`도 게이트웨이 세션에서는 Fable 5로 풀리는 경우가 있어, 확실히 하려면 전체 ID(`claude-fable-5-1`)를 쓴다.
- 관리자 제한. 조직 설정에서 `availableModels` / `deniedModels`로 막혀 있으면 `--model`로 골라도 거부된다.
- 1M 컨텍스트는 모델 이름 뒤에 `[1m]` 접미사로 지정한다. 표준 가격과 같다(Haiku 5.5만 100K 초과분 단가가 오른다).
- Explore 같은 내장 에이전트는 메인이 Fable이어도 연결 방식에 따라 Opus로 돌 수 있다. 내장 에이전트까지 통제하려면 환경변수 `CLAUDE_CODE_SUBAGENT_MODEL`을 쓴다.

## 정리

모델 선택은 "어떤 모델이 좋은가"가 아니라 "이 작업에 어느 급이 필요한가"의 문제다.

- 메인 세션은 Opus를 기본으로 두고, `/model fable`은 막힌 구간을 몰아서 처리할 때만.
- 서브에이전트는 정의 파일에 평소 값을 박는다. 구현·리뷰 Opus, QA Haiku.
- 보안 리뷰처럼 예외적으로 더 강한 모델이 필요하면 호출 시점에 올린다. 정의 파일은 건드리지 않는다.
- 정책에는 날짜와 근거를 남긴다. 라인업은 바뀐다.

설정 자체는 10분이면 끝난다. 오래 걸리는 건 "지금 이 턴에 최상위 모델이 필요한가"를 매번 생각하는 습관 쪽이다.

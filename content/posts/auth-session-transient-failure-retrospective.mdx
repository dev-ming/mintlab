"페이지 이동하다가 갑자기 로그아웃돼요"라는 제보에서 시작했다. 원인을 파보니 서버 3건, 클라이언트 2건으로 갈렸고, 다섯 건이 전부 "실패를 어떻게 해석할 것인가" 라는 하나의 질문에 걸려 있었다. 서버 쪽은 반영이 끝났고 클라이언트 반영은 아직 남아 있다. 구현 전에 원인 분석과 설계 결정을 남겨두는 기록이다.

증상은 세 갈래로 들어왔다.

- 쓰다가 페이지 이동하면 갑자기 로그아웃
- 링크를 새 탭으로 열면 로그인이 안 되어 있음
- 메신저 인앱 브라우저로 들어오면 매번 게스트

세 개가 다른 버그처럼 보였지만 원인은 두 개였다.

---

## 1. 실패를 전부 `false`로 뭉갠 대가

액세스 토큰이 만료되면 401이 오고, 리프레시 토큰으로 재발급받아 원래 요청을 재시도한다. 흔한 구조다. 문제는 재발급 함수의 반환 타입이었다.

```ts
async function tryRefreshTokens(): Promise<boolean> {
  const refreshToken = getStoredRefreshToken();
  if (!refreshToken) return false;              // ① 토큰이 없다
  try {
    const res = await fetch(`${baseUrl}/api/v1/auth/refresh`, { ... });
    if (!res.ok) return false;                  // ② 401도, 500도, 503도 전부 여기
    ...
    return true;
  } catch {
    return false;                               // ③ 네트워크 오류·타임아웃·CORS
  }
}
```

호출부는 이렇다.

```ts
if (response.status === 401) {
  const refreshed = await tryRefreshTokens();
  if (!refreshed) {
    clearSessionAndRedirectToHome();            // ← 무조건 로그아웃
    return response;
  }
  ...
}
```

`boolean`은 "인증이 무효다" 와 "지금은 확인할 수 없다" 를 구분하지 못한다. 그런데 코드는 둘을 같은 결말로 보냈다.

| 재발급이 실패한 이유 | 올바른 대응 | 실제 동작 |
|---|---|---|
| 리프레시 토큰 만료·폐기 (401/403) | 로그아웃 | 로그아웃 ✅ |
| API 서버 재배포 중 (502/503) | 잠시 후 재시도, 세션 유지 | 로그아웃 ❌ |
| 지하철·엘리베이터 네트워크 순단 | 재시도, 세션 유지 | 로그아웃 ❌ |
| 세션 저장소(캐시 서버) 장애 | 대기, 세션 유지 | 로그아웃 ❌ |

액세스 토큰 만료는 정상적으로 주기가 돌아온다. 하필 그 재발급 요청이 순단과 겹치면 로그아웃이다. 평소엔 멀쩡하다가 가끔 튕기는 전형적인 간헐적 버그의 모양이 여기서 나왔다.

서버 쪽도 이에 맞춰, 세션 저장소가 죽었을 때 401 대신 503 + 전용 에러 코드를 내려주도록 바꿨다. 401("네 자격증명이 틀렸다")과 503("내가 지금 확인을 못 한다")은 클라이언트가 완전히 다르게 반응해야 하는 상태인데, 그동안은 서버도 클라이언트도 이를 뭉개고 있었다.

> 인증 처리에서 세션을 파기해도 되는 유일한 경우는, 서버가 명시적으로 "이 자격증명은 무효다"라고 답했을 때뿐이다. 그 외 전부 — 네트워크 오류, 5xx, 타임아웃, CORS 실패 — 는 "모르겠다"이고, 모를 때의 기본값은 *유지*여야 한다.

`Promise<boolean>`을 `Promise<'ok' | 'invalid' | 'unavailable'>` 같은 3-state로 바꾸는 것만으로 설계 의도가 타입에 박힌다. 불리언은 두 갈래처럼 보이지만, 인증에서 실패는 항상 두 종류다.

## 2. `sessionStorage`는 탭의 것이지 사용자의 것이 아니다

토큰을 `sessionStorage`에 넣고 있었다. XSS 노출 시간을 줄이려는 선택이었지만, 부작용이 컸다.

| | localStorage | sessionStorage | httpOnly 쿠키 |
|---|---|---|---|
| 새 탭에서 공유 | ✅ | ❌ 탭마다 독립 | ✅ |
| 새로고침 후 유지 | ✅ | ✅ | ✅ |
| JS에서 접근 (= XSS 노출) | 노출 | 노출 | 불가 |
| 요청에 자동 첨부 | ❌ 수동 | ❌ 수동 | ✅ 자동 |

새 탭은 스토리지가 빈 상태로 시작한다. 그래서 링크를 새 탭으로 열면 로그인한 적 없는 사용자처럼 보인다.

더 아픈 건 인앱 브라우저였다. 메신저나 SNS 앱에서 링크를 누르면 매번 새 웹뷰가 뜬다. 새 탭과 같은 조건이다. 즉 *공유 링크를 타고 들어오는 유입 경로 전체가 항상 로그아웃 상태로 보였다.* 가장 중요한 유입에서 가장 나쁜 첫인상을 주고 있었던 셈이다.

해결 방향은 리프레시 토큰을 httpOnly 쿠키로 옮기고, 부팅 시 한 번 재발급을 돌려 액세스 토큰을 복구하는 것이다. 쿠키는 브라우저 단위라 새 탭·새 웹뷰에도 따라간다.

부팅 복구에는 조건이 두 개 붙는다.

- 페이지 로드당 1회로 제한 — 안 그러면 컴포넌트가 마운트될 때마다 재발급이 돈다.
- "세션 없음"이 확정된 경우에만 캐시 — 서버가 4xx로 "그런 세션 없다"고 답했을 때만 게스트로 확정한다. 5xx나 네트워크 오류로 실패한 걸 캐시하면, 1막과 똑같이 순단을 로그아웃으로 오해하는 코드가 하나 더 늘어난다.

## 3. 정본이 둘이 되는 순간

쿠키로 옮기면서 하위호환을 위해 요청 본문의 `refreshToken`도 폴백으로 남겨뒀다. 마이그레이션 기간의 안전장치처럼 보이지만, 여기에 함정이 있다.

쿠키는 브라우저당 하나, `sessionStorage`는 탭당 하나다.

```
탭 A: 계정 1로 로그인  → sessionStorage(탭A) = 계정1 토큰
탭 B: 계정 2로 로그인  → sessionStorage(탭B) = 계정2 토큰
                        쿠키(브라우저 공용) = 계정2 토큰  ← 마지막 로그인이 덮어씀

탭 A에서 재발급 요청 → 쿠키(계정2)와 본문(계정1)이 함께 감
                     → 서버가 어느 쪽을 먼저 읽느냐에 따라 결과가 갈림
```

탭 A가 계정 2의 세션을 받아올 수 있다. QA에서 재현하기 어렵고, 재현되면 심각한 종류의 버그다.

> 인증 자격증명의 정본은 하나여야 한다. 하위호환 폴백은 "구버전 클라이언트를 위한 배려"처럼 보이지만, 두 저장소의 수명과 범위가 다르면 폴백이 아니라 경합이다.

그래서 "쿠키를 정본으로 삼는다"와 "`sessionStorage`에 리프레시 토큰을 저장하지 않는다"는 같은 릴리스로 나가야 한다. 둘을 나눠 배포하면 그 사이 기간이 정확히 위 시나리오다.

## 4. 한 줄이 전부를 좌우한다

서버가 쿠키를 완벽하게 심어도, 클라이언트가 이 한 줄을 빠뜨리면 전부 무효다.

```diff
- await fetch(url, { method: 'POST', headers });
+ await fetch(url, { method: 'POST', headers, credentials: 'include' });
```

`fetch`는 크로스 오리진에서 기본적으로 쿠키를 보내지도, 받지도 않는다. 서버가 `Set-Cookie`를 내려줘도 브라우저가 조용히 버린다. 에러도 경고도 없다. 프론트와 API가 다른 오리진(포트만 달라도 크로스 오리진이다)인 구조에서는 반드시 명시해야 한다.

서버 쪽도 세트로 맞아야 한다.

- `Access-Control-Allow-Credentials: true`
- `Access-Control-Allow-Origin`에 와일드카드 금지 (credentials와 함께 쓸 수 없다 — 정확한 오리진을 적어야 한다)
- 사이트가 다르면 쿠키에 `SameSite=None; Secure`

이 조합 중 하나만 빠져도 쿠키는 조용히 사라진다. "서버는 다 했는데 왜 안 되지"의 대부분이 여기다.

## 5. 가드도 "모름"을 표현할 수 있어야 한다

인증 가드가 이런 모양이었다.

```ts
const token = sessionStorage.getItem(ACCESS_TOKEN_KEY);
if (!token) {
  router.replace('/');   // 즉시 추방
  return;
}
```

1막과 같은 문제의 다른 얼굴이다. 가드가 있다/없다 두 상태만 안다. 부팅 복구를 도입하면 세 번째 상태가 생긴다.

```
확인 중  →  (복구 성공) 로그인
         →  (서버가 세션 없음 확정) 게스트
```

"확인 중"을 표현하지 못하면, 복구가 끝나기 전에 가드가 먼저 판단해버려서 새 탭에서 로그인 사용자가 그대로 튕긴다. 쿠키를 도입해도 증상이 안 고쳐지는 결말이다.

같은 가드의 에러 처리도 손봐야 한다.

```ts
.catch(() => router.replace('/'))   // 네트워크 오류 = 추방
```

또 1막이다. 이 패턴은 코드베이스 여기저기에 복제되어 있었다. 한 곳에서 잘못된 기본값을 정하면, 그 기본값이 복사되어 퍼진다.

## 배운 점

1. 인증에서 실패는 항상 두 종류다 — "무효다"와 "모르겠다". 이걸 `boolean` 하나로 표현하는 순간, 코드는 반드시 둘을 같게 취급하게 된다. 타입에서 갈라놓으면 호출부가 강제로 분기한다.
2. 모를 때의 기본값은 "유지"다. 파괴적인 동작(로그아웃, 삭제, 초기화)의 기본값을 "실패 시"에 두면, 인프라가 흔들릴 때마다 사용자 데이터가 날아간다.
3. 저장소의 수명과 범위를 먼저 정한다. 탭 단위(`sessionStorage`) / 브라우저 단위(쿠키·`localStorage`) / 요청 단위(메모리)는 보안 특성만 다른 게 아니라 "누구의 것인가" 가 다르다. 세션은 사용자의 것이지 탭의 것이 아니다.
4. 정본은 하나만. 하위호환 폴백은 마이그레이션을 부드럽게 해주는 대신, 두 저장소의 범위가 다르면 경합을 만든다. 폴백을 남길 거면 "언제 제거할지"를 같이 정해야 한다.
5. 서버 작업과 클라이언트 작업이 세트인 변경은 세트로 배포한다. 쿠키를 심는 쪽만 나가면 아무 효과가 없고, 저장을 멈추는 쪽만 나가면 로그인이 깨진다.
6. 잘못된 기본값은 복제된다. "실패하면 로그아웃"이 한 군데 있으면 다섯 군데 있다. 하나 고칠 때 같은 패턴을 전부 찾는 게 맞다.

운영 사이트맵에 URL이 21개뿐이었다. 정적 페이지 7개 × 3개 언어. 기사도, 상세 페이지도 하나도 없었다. 코드에는 분명 API로 목록을 받아 붙이는 로직이 있는데.

"환경변수가 빠졌겠지"로 시작해서, 그게 아니라는 걸 증명하고, 진짜 원인이 빌드 시점 생성 + 조용한 예외 처리의 조합이었다는 데까지 간 기록이다.

---

## 코드는 멀쩡해 보였다

```ts
// app/sitemap.ts
export const revalidate = 3600;

async function fetchJson(url: string) {
  try {
    const res = await fetch(url, { next: { revalidate: 3600 } });
    if (!res.ok) return null;
    return await res.json();
  } catch {
    return null;               // ← 여기가 범인이었다
  }
}

export default async function sitemap() {
  const staticEntries = STATIC_PATHS.flatMap(urlsForAllLocales);
  const [articles, items] = await Promise.all([articleEntries(), itemEntries()]);
  return [...staticEntries, ...articles, ...items];
}
```

조회에 실패하면 정적 경로만으로 폴백한다. 의도적인 설계였고, 주석에도 그렇게 적혀 있었다. 문제는 실패했다는 사실이 아무 데도 남지 않는다는 것이었다.

---

## 1막: 틀린 가설을 빨리 버리기

가장 그럴듯한 가설은 "빌드 환경에 API 주소 환경변수가 없다"였다. 그러면 기본값(`localhost`)으로 떨어져 전부 실패하니까 증상과 맞는다.

확인은 두 가지로 했다.

하나, 번들에 박힌 값 보기. 클라이언트에 노출되는 환경변수는 빌드 시점에 코드로 인라인된다. 그러니 배포된 JS 청크를 받아서 grep하면 빌드에 무슨 값이 들어갔는지 그대로 보인다.

```bash
curl -s https://example.com/ | grep -oE 'src="/_next/static/chunks/[^"]+"' | head -8 \
  | while read c; do curl -s "https://example.com$c" | grep -ohE 'https://[a-z.-]*api[a-z.-]*'; done | sort -u
# → https://api.example.com
```

값은 정상이었다. 가설 하나 탈락.

둘, API를 직접 두드리기. 사이트맵이 쓰는 엔드포인트를 그대로 호출했더니 200에 데이터도 정상. 가설 완전 탈락.

> 배포된 번들을 grep하는 건 "빌드에 어떤 환경변수가 들어갔나"를 확인하는 가장 빠른 방법이다. 콘솔 접근 권한이 없어도 된다.

여기서 배운 것: 증상에 맞는 가설이라고 맞는 가설은 아니다. 반증이 싸게 가능하면 먼저 반증해봐야 한다.

## 2막: 진짜 원인은 "언제 만들어지는가"였다

빌드 로그의 라우트 표를 다시 봤다.

```
Route (app)                     Revalidate  Expire
└ ○ /sitemap.xml                       1h      1y

○  (Static)   prerendered as static content
```

`○`. 이 라우트는 빌드 시점에 한 번 만들어지는 정적 파일이었다. `revalidate`가 붙어 있어도 첫 생성은 빌드 때다.

그래서 실제로 벌어진 일은 이랬다.

1. 빌드 시점에 API 조회가 실패한다 (그때 API가 잠깐 안 닿았든, 빌드 환경에서 못 나가든)
2. `catch`가 조용히 삼킨다. 빌드는 성공한 채로 끝난다
3. 정적 경로만 담긴 XML이 만들어져 CDN에 올라간다
4. 그게 계속 서빙된다

한 번의 일시적 실패가 영구적인 결과물로 굳어버린 것이다. 그리고 로그가 없으니 아무도 그 순간을 모른다.

## 3막: 고친 것

### 요청 시점 생성으로 전환

```ts
- export const revalidate = 3600;
+ export const dynamic = 'force-dynamic';
```

라우트가 `○ (Static)`에서 `ƒ (Dynamic)`으로 바뀐다. 요청마다 서버에서 생성되니 빌드 때의 실패가 결과물로 남지 않는다. 다음 요청에서 자연히 회복된다.

개별 `fetch`의 `next: { revalidate: 3600 }`은 그대로 뒀다. 페이지는 동적이지만 데이터는 1시간 캐시되므로, 크롤러가 몰려와도 API를 매번 때리지 않는다. "페이지 렌더링 시점"과 "데이터 신선도"를 따로 제어하는 게 요점이다.

검증은 배포 전에 빌드 로그로 했다.

```
└ ƒ /sitemap.xml       ← ○ 에서 바뀐 것 확인
```

응답 헤더로도 확인된다. 동적 라우트는 `cache-control: public, max-age=0, must-revalidate`가 붙는다.

### 실패를 보이게 만들기

```ts
if (!res.ok) {
  console.warn(`[sitemap] ${res.status} ${res.statusText} — ${url}`);
  return null;
}
} catch (e) {
  console.warn(`[sitemap] fetch failed — ${url}`, e);
  return null;
}
```

이게 사실 더 중요한 변경이었다. 폴백 자체는 옳은 설계다 — 사이트맵 하나 때문에 페이지가 죽으면 안 되니까. 하지만 폴백과 침묵은 다른 문제다.

로그 형태만으로 원인이 갈리게 만든 것도 의도였다.

| 로그 | 의미 |
| --- | --- |
| `[sitemap] 403 Forbidden — https://...` | 요청은 닿았고 앱/방화벽 레벨에서 거부 |
| `[sitemap] fetch failed — ... ETIMEDOUT` | 아예 못 닿음. 방화벽이 조용히 드롭 |
| `[sitemap] fetch failed — ... ENOTFOUND` | DNS 실패 |
| `[sitemap] fetch failed — ... ECONNREFUSED` | 닿았는데 거부 |

로그 한 줄을 어떻게 쓰느냐로, 나중에 누군가 원인을 몇 분 만에 좁힐 수 있는지가 갈린다.

## 4막: 개발환경은 되는데 운영은 안 되는 이유

고치고 배포했더니 개발 환경 사이트맵은 21개 → 156개가 됐다. 그런데 스테이징은 그대로 21개였다.

같은 코드, 같은 커밋. 차이는 서버가 API를 어떤 경로로 부르느냐였다.

```ts
const SERVER_API_BASE_URL = process.env.SSR_API_BASE_URL ?? PUBLIC_API_BASE_URL;
```

- 개발 환경: 컨테이너들이 한 네트워크에 있어서 내부 주소(`http://api:3200`)로 부른다. 공인망을 안 탄다
- 스테이징/운영: 서버리스 SSR이라 내부망이 없다. 공인 도메인으로 나간다. 그 요청은 클라우드 사업자가 관리하는, 예측 불가능한 IP에서 출발한다

API 앞단에 IP 허용목록이 있으면 브라우저는 되고 서버만 막힌다. 사내에서 `curl`을 때려보면 200이 나오니 "API는 멀쩡한데?" 싶지만, 그건 내 IP가 허용목록에 있어서였다.

여기서 놓치기 쉬운 함정: 서버리스 컴퓨트의 egress IP는 고정이 아니다. "IP 하나 열어주면 되지"가 성립하지 않는다. 선택지는 셋뿐이다.

1. VPC + NAT 게이트웨이로 고정 IP를 만들어 그것만 허용
2. IP 대신 공유 시크릿 헤더로 인증 (코드 수정 필요)
3. 서버→서버 호출을 사설 주소로 돌리기 (컴퓨트가 VPC에 붙어 있어야 함)

---

## 남는 것

폴백은 설계, 침묵은 버그다. 조용히 삼키는 `catch`는 장애를 "정상적으로 비어 있는 상태"로 위장시킨다. 폴백을 유지하되 흔적은 남겨야 한다.

"빌드 때 만들어지는가, 요청 때 만들어지는가"는 기능의 성격에 따라 정해야 한다. 외부 상태에 의존하는 산출물을 빌드 시점에 고정하면, 그 순간의 일시적 실패가 영구화된다. 빌드 로그의 라우트 표에서 `○`인지 `ƒ`인지는 한 번쯤 확인할 가치가 있다.

환경별로 네트워크 경로가 다르면 "코드는 같은데 결과가 다른" 버그가 나온다. 개발 환경이 내부망 지름길을 쓰고 있다면, 그 지름길이 상위 환경에는 없다는 걸 전제로 설계해야 한다. 개발 환경에서 잘 되는 것이 오히려 상위 환경의 문제를 가려버린다.

반증이 싼 가설부터 죽인다. 배포된 번들 grep, API 직접 호출 — 둘 다 몇 분이면 되는데 가장 그럴듯한 가설을 깨끗하게 탈락시켰다. 그 덕에 엉뚱한 곳을 오래 파지 않았다.

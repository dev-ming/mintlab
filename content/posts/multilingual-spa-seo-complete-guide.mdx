앱은 잘 도는데 검색에는 안 나온다. 사이트맵도 올렸고 메타 태그도 넣었는데 며칠이 지나도 색인된 건 URL 한 개뿐. 이 상태를 하나씩 뜯어보며 정리한 글이다.

SEO를 "메타 태그 넣기"로만 생각하면 절반은 놓친다. 실제로는 역할이 다른 네 층이 있고, 각 층에서 조용히 실패하는 지점이 따로 있다.

---

## 0. 네 층을 먼저 구분한다

| 층 | 답하는 질문 | 형태 |
| --- | --- | --- |
| robots.txt | 크롤러가 들어와도 되나 | 사이트 루트 파일 |
| sitemap.xml | 어떤 URL들이 있나 | 사이트 루트 파일 |
| 메타데이터 · 공유 카드 | 이 페이지는 무엇이고 어떻게 보여줄까 | 페이지별 `<head>` |
| canonical · hreflang | 이 URL들끼리 무슨 관계인가 | 페이지별 `<head>` |

핵심은 아래 두 층이 서로 대체할 수 없다는 것이다. 사이트맵에 URL을 아무리 채워도 페이지 사이의 관계는 각 페이지가 직접 말해야 한다. 이걸 헷갈리면 "사이트맵 다 넣었는데 왜 색인이 안 되지?"에서 막힌다.

---

## 1. robots.txt — 문 열기

```
User-Agent: *
Allow: /
Disallow: /en/account
Disallow: /en/signup
Disallow: /en/auth
Disallow: /es/account
...
Sitemap: https://example.com/sitemap.xml
```

로그인 후 화면, 가입 절차, 인증 콜백처럼 크롤러가 볼 이유가 없는 경로를 막는다. 다국어면 언어별로 전부 적어야 한다 — 로케일이 URL 앞에 붙는 구조라면 경로 하나당 언어 수만큼 줄이 늘어난다.

마지막 `Sitemap:` 줄이 중요하다. 검색 콘솔에 따로 제출하지 않아도 크롤러가 여기서 사이트맵을 찾는다.

확인할 점 — 개발·스테이징 환경이 `Allow: /`로 열려 있으면 그쪽도 크롤링된다. 상위 환경과 같은 코드를 쓰면 자동으로 열리므로 환경별로 막을지 정해야 한다.

---

## 2. sitemap.xml — 목록 주기

URL 목록이다. "이런 페이지들이 있으니 와서 봐라"까지가 역할이고, 색인을 보장하지 않는다.

정적 경로 + API로 받아온 동적 상세(기사·상품·게시물 등)를 합쳐 만든다. 여기서 크게 두 번 넘어졌다.

하나, 생성 시점. 빌드 때 한 번 만들어지는 구조라 그 순간의 API 실패가 결과물로 굳어버렸다. → [사이트맵에 상세 페이지가 하나도 없던 이유](/posts/nextjs-sitemap-build-time-failure-retrospective)에 따로 정리

둘, 링크로만 닿는 페이지 누락. 정적 경로를 배열로 손수 관리하고 있었다.

```ts
const staticPaths = ['', '/section-a', '/section-b', '/terms', '/privacy'];
```

여기에 앱 메인 화면이 없었다. 랜딩(`''`)에서 링크를 타고 들어가는 화면인데, 그 하위 목록들(`/section-a`)만 적고 정작 부모 경로를 빠뜨렸다. 목록을 손으로 관리하면 이런 누락이 생긴다.

재밌는 건 결과다. 크롤러는 링크를 타고 그 페이지를 스스로 찾아 색인까지 했다. 사이트맵에 정성껏 넣어둔 URL들은 아직 하나도 색인 안 된 상태에서. 사이트맵은 "발견을 돕는 힌트"일 뿐 크롤러의 유일한 입구가 아니라는 게 그대로 드러났다.

> 정적 경로는 라우트 정의에서 자동 생성하거나, 최소한 "공개 페이지 목록"을 한곳에서 관리하는 게 안전하다.

## 3. 메타데이터와 공유 카드 — 뭐라고 보여줄지

프레임워크가 페이지별로 `<head>`를 만들어주는 API를 제공한다. 여기서 세 가지를 배웠다.

### 객체 필드는 깊은 병합되지 않는다

레이아웃에 공통 공유 카드 설정을 두고 페이지에서 일부만 덮어쓰면, 페이지 것이 통째로 이긴다.

```ts
// 레이아웃
openGraph: { siteName, type, locale, images: [기본이미지] }

// 페이지 — images를 안 적으면 기본 이미지도 함께 사라진다
openGraph: { title, description }
```

그래서 공유 카드 설정을 정의하는 페이지는 매번 이미지까지 다시 넣어야 한다. 이걸 모르면 "왜 이 페이지만 카드가 비지?"를 한참 찾는다. 공통 빌더 함수를 하나 만들어 모든 페이지가 그걸 통과하게 하는 편이 낫다.

### 상속을 설계에 활용한다

반대로 이 성질을 이용하면, 정의하지 않은 페이지는 자동으로 기본값을 상속한다. 페이지가 수십 개일 때 전부 개별 정의할 필요가 없다. 기본 문구를 로케일 레이아웃에 두고, 고유 문구가 필요한 페이지만 덮어쓰면 된다.

### 동적 페이지는 서버에서 데이터를 받아야 한다

상세 페이지의 제목·이미지는 API에서 와야 한다. 이 조회는 서버에서 일어나므로, 클라이언트가 쓰는 공개 주소와 서버가 쓰는 주소가 다를 수 있다는 걸 전제해야 한다.

```ts
const serverApiBase = process.env.INTERNAL_API_BASE ?? publicApiBase;
```

여기서 조회가 실패하면 조용히 기본 메타데이터로 폴백된다. 페이지는 정상으로 보이고 공유 카드만 밋밋해지므로 아무도 눈치채지 못한다. 사이트맵과 똑같은 함정이다.

## 4. canonical과 hreflang — 관계 말하기

다국어 서비스라면 여기가 제일 중요하다. 앞의 세 층을 다 해놓고 이걸 빼면 색인이 안 된다.

### canonical — "이게 원본이다"

같은 내용에 여러 주소로 닿을 수 있을 때 대표를 지정한다.

```html
<link rel="canonical" href="https://example.com/es" />
```

웹에서는 같은 페이지가 쉽게 여러 주소를 갖는다.

```
/es
/es?utm_source=...        ← 유입 추적 파라미터가 붙은 링크
/es/                      ← 슬래시 유무
```

canonical이 없으면 검색엔진은 셋을 다른 페이지로 보고 평가 점수를 쪼갠다. 초대·공유 기능이 있어 추적 파라미터가 붙은 링크가 계속 생기는 서비스라면 반드시 필요하다.

### hreflang — "같은 페이지의 다른 언어판이다"

```html
<link rel="alternate" hreflang="en"        href="https://example.com/en" />
<link rel="alternate" hreflang="es-419"    href="https://example.com/es" />
<link rel="alternate" hreflang="pt-BR"     href="https://example.com/pt" />
<link rel="alternate" hreflang="x-default" href="https://example.com/en" />
```

두 가지 일을 한다.

중복이 아니라고 알린다. 언어판들은 구조가 같고 텍스트만 다르다. hreflang이 없으면 "같은 페이지 여러 벌"로 판단해 하나만 대표로 색인하고 나머지를 버린다.

사용자 언어에 맞는 판을 띄운다. 지역·언어 설정에 맞는 URL을 검색 결과에 노출한다. 없으면 검색엔진이 임의로 고른다.

`x-default`는 "위 어디에도 안 맞으면 이걸"이라는 기본값이다.

> 지역 변종 표기(`es-419` = 중남미 스페인어, `pt-BR` = 브라질 포르투갈어)는 타깃 지역이 분명하면 써주는 게 좋다. 단순 `es`·`pt`보다 매칭이 정확해진다.

### 실제로 이렇게 드러났다

사이트맵을 제출하고 며칠 뒤, 색인된 URL이 딱 하나였다. 그것도 사이트맵에 없던 페이지, 언어판 중 하나. 랜딩과 기사 상세에만 canonical·hreflang이 있고 나머지 페이지엔 없는 상태였다.

- 언어판 여럿 중 하나만 색인 → hreflang 부재의 전형적인 증상
- 사이트맵에 넣은 URL은 아직 미색인 → 사이트맵은 색인을 보장하지 않는다는 증거

메타데이터를 넣을 때 canonical·hreflang을 함께 넣어야 한다. 나는 "공유 카드 문구"라는 요구사항에만 맞춰 메타데이터만 채우고 이 둘을 범위 밖이라며 뒤로 미뤘는데, 색인 관점에서는 이쪽이 먼저였다.

## 5. 환경이 갈리는 지점

같은 코드가 개발·스테이징·운영에서 다르게 동작하는 자리가 SEO에는 유독 많다.

기준 URL(base URL). 절대 URL을 만들 때 쓰는 값이다. 환경변수가 없으면 보통 하드코딩된 기본값으로 떨어지는데, 그 기본값이 운영 도메인이면 개발 환경 사이트맵이 운영 URL을 광고하게 된다. 실제로 개발 환경의 robots.txt가 운영 사이트맵을 가리키고 있었다.

```
개발 환경 robots.txt → Sitemap: https://운영도메인/sitemap.xml
```

같은 값이 공유 카드 이미지의 절대 URL 변환에도 쓰이므로, 여기가 틀리면 카드 이미지도 다른 환경을 가리킨다.

서버에서 API로 나가는 경로. 개발 환경은 컨테이너 내부 주소를 쓰고 상위 환경은 공인 도메인을 쓰는 구성이 흔하다. API 앞단에 IP 제한이 있으면 브라우저는 되고 서버만 막힌다. 이때 동적 사이트맵과 상세 페이지 메타데이터가 동시에 조용히 비어버린다. 사내망에서 직접 호출해보면 잘 되니까 "API는 멀쩡한데?"라고 넘어가기 쉽다.

## 6. 검증 — 브라우저 없이 확인하는 법

배포된 결과는 `curl`만으로 대부분 확인된다.

```bash
# 사이트맵 URL 개수와 구성
curl -s https://example.com/sitemap.xml | grep -c '<loc>'

# 특정 URL이 실제로 들어 있는지 (부분 일치에 속지 않도록 정확히)
curl -s https://example.com/sitemap.xml | grep -o '<loc>[^<]*</loc>' \
  | sed 's/<[^>]*>//g' | grep -x "https://example.com/es"

# canonical·hreflang 유무
curl -s https://example.com/es | grep -oE '<link rel="(canonical|alternate)"[^>]*>'

# 공유 카드 태그
curl -s https://example.com/es | grep -oE '<meta property="og:[a-z:]+" content="[^"]*"'

# 사이트맵이 정적 파일인지 요청마다 생성인지
curl -sI https://example.com/sitemap.xml | grep -i cache-control

# 빌드에 어떤 공개 환경변수가 박혔는지 (번들에 인라인된다)
curl -s https://example.com/ | grep -oE 'src="/_next/static/[^"]+"' | head -8 \
  | while read c; do curl -s "https://example.com$c" | grep -ohE 'https://[a-z.-]+'; done | sort -u
```

URL을 찾을 때 정확히 일치(`grep -x`)로 확인하는 습관이 중요하다. 부분 일치로 보면 하위 경로가 걸려서 "있네" 하고 넘어가는데, 그 순간 진단이 통째로 어긋난다. 실제로 그것 때문에 헛다리를 짚을 뻔했다.

## 7. 체크리스트

robots.txt
- [ ] 비공개 경로를 언어별로 모두 차단했는가
- [ ] `Sitemap:` 줄이 그 환경의 도메인을 가리키는가

sitemap.xml
- [ ] 링크로만 닿는 페이지(앱 메인 등)가 빠지지 않았는가
- [ ] 빌드 시점 고정이 아니라 요청 시점 생성인가
- [ ] 동적 목록 조회 실패가 로그에 남는가
- [ ] 상세 페이지 종류를 다 넣었는가

메타데이터 · 공유 카드
- [ ] 공유 카드를 정의한 페이지가 이미지도 함께 넣었는가 (깊은 병합 안 됨)
- [ ] 기본값 상속 구조가 의도대로인가
- [ ] 동적 페이지의 서버 조회 실패를 감지할 수 있는가
- [ ] 절대 URL 기준값이 환경별로 맞는가

canonical · hreflang
- [ ] 색인 대상 페이지 전부에 canonical이 있는가
- [ ] 언어판이 서로를 hreflang으로 가리키는가
- [ ] `x-default`가 있는가
- [ ] 지역 변종 표기가 타깃 시장과 맞는가

운영
- [ ] 사이트맵 내용이 바뀌면 검색 콘솔에 재제출했는가
- [ ] 색인 현황을 며칠 단위로 관찰하고 있는가 (하루 이틀로 판단하지 않는다)

## 남는 것

사이트맵은 힌트고, 관계는 페이지가 말한다. 목록에 URL을 넣는 것과 그 URL들이 서로 무슨 관계인지 알리는 것은 완전히 다른 일이다. 색인이 안 될 때 사이트맵부터 의심하게 되는데, 다국어라면 hreflang을 먼저 보는 게 빠르다.

SEO 실패는 조용하다. 사이트맵이 비어도, 메타데이터가 폴백돼도 페이지는 정상으로 보인다. 사용자도 개발자도 모른다. 그래서 실패를 로그로 남기고 배포 후 실제 응답을 확인하는 절차가 다른 기능보다 더 필요하다.

숫자가 아니라 패턴을 본다. 새 사이트가 몇 달에 걸쳐 천천히 색인되는 건 정상이라 "며칠째 몇 건"만으로는 아무것도 판단할 수 없다. 반면 "언어판 여럿 중 하나만"처럼 규칙이 보이는 결과는 시간이 해결해주지 않는다. 구성 문제다.

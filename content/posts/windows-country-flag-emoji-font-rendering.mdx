사용자가 쓴 글에 국기 이모지를 넣었는데, 어떤 사람 화면에서는 국기가 뜨고 어떤 사람 화면에서는 알파벳 두 글자로 보인다. 버그 리포트로 올라오기 딱 좋은 현상인데, 원인은 코드가 아니라 폰트에 있다.

---

## 0. 현상

같은 문자열인데 환경마다 다르게 보인다.

```
입력:  우리 함께 응원해요 🇰🇷

macOS / iOS / Android  →  우리 함께 응원해요 🇰🇷
Windows (Chrome/Edge)  →  우리 함께 응원해요 KR      ← 글자로 보임
```

처음엔 인코딩이 깨졌나, DB에서 잘렸나 의심하게 되는데 둘 다 아니다. 문자열은 멀쩡히 저장돼 있고 전달도 잘 된다. 그릴 글자가 없을 뿐이다.

---

## 1. 국기 이모지는 단일 문자가 아니다

이게 핵심이다. 웃는 얼굴 `😀`는 코드포인트 하나(U+1F600)지만, 국기는 문자 두 개의 조합이다.

```
🇰🇷  =  U+1F1F0  +  U+1F1F7
         (🇰)        (🇷)
```

이 두 문자를 Regional Indicator Symbol이라고 한다. U+1F1E6부터 U+1F1FF까지 26개가 알파벳 A–Z에 대응한다. 국가 코드(ISO 3166-1 alpha-2)를 이 문자로 옮겨 나란히 쓰면 국기가 된다.

```
KR → 🇰 + 🇷 → 🇰🇷
JP → 🇯 + 🇵 → 🇯🇵
```

여기서 "나란히 쓰면 국기가 된다"를 누가 해주느냐가 문제다. 유니코드는 "이 두 글자가 붙어 있으면 국기로 그려라"라고 정의만 할 뿐, 실제로 두 글자를 하나의 국기 그림으로 합치는 건 폰트의 몫이다.

폰트에 그 합성 규칙과 국기 글리프가 없으면? 폰트는 아는 대로만 그린다 — 낱개 문자 두 개. 그게 알파벳 두 글자로 보이는 정체다.

---

## 2. 왜 하필 Windows인가

Windows의 기본 이모지 폰트(Segoe UI Emoji)에는 국기 글리프가 들어 있지 않다. 빠진 게 아니라 넣지 않은 쪽에 가깝다. 국기는 영토·주권 분쟁과 얽히기 쉬워서, 전 세계에 배포되는 OS 폰트에 담기 부담스러운 자산이다.

그래서 환경별로 이렇게 갈린다.

| 환경 | 국기 표시 | 이유 |
| --- | --- | --- |
| macOS · iOS | ✅ | Apple Color Emoji에 국기 포함 |
| Android | ✅ | Noto Color Emoji에 국기 포함 |
| Windows + Chrome/Edge | ❌ | OS 폰트에 국기 글리프 없음 |
| Windows + Firefox | ✅ | 브라우저가 자체 이모지 폰트를 번들 |

같은 Windows인데 브라우저마다 다른 게 결정적인 힌트다. 브라우저가 자기 폰트를 들고 오면 보인다 — 즉 폰트만 공급하면 해결된다는 뜻이다.

> 참고로 이건 국기만의 문제다. 다른 이모지는 Windows에서도 잘 보인다. 그래서 "이모지가 안 나온다"가 아니라 "국기만 안 나온다"로 증상을 좁히는 게 진단의 시작이다.

---

## 3. 확인하는 법

추측하지 말고 코드포인트를 직접 뜯어보면 된다.

```js
[...'🇰🇷'].map((c) => c.codePointAt(0).toString(16));
// → ['1f1f0', '1f1f7']   ← 두 개면 정상. 데이터는 멀쩡하다
```

여기서 두 개가 나오면 데이터 문제가 아니다. 저장·전송은 정상이고 렌더링 단계의 문제로 확정된다. 반대로 값이 깨져 있다면 그건 인코딩 이슈라 완전히 다른 수사 방향이다.

---

## 4. 해결책 A — 국기 구간만 다른 폰트에 넘기기 (실제로 쓴 방법)

CSS `unicode-range`로 Regional Indicator 영역만 별도 폰트가 담당하게 한다. 원리는 이렇다.

```css
@font-face {
  font-family: 'Flag Font';
  src: url('/fonts/flags.woff2') format('woff2');
  unicode-range: U+1F1E6-1F1FF;   /* 국기 조합 문자만 */
}

body {
  font-family: 'Flag Font', 'MyBodyFont', system-ui, sans-serif;
}
```

폰트 이름이 스택 맨 앞이어야 한다. 직관과 반대라 실수하기 쉬운 지점이다. 뒤에 두면 앞 폰트가 "나도 그 문자 그릴 수 있다"고 주장하는 순간(글리프가 없어도 .notdef로 처리) 국기가 그쪽으로 넘어가버린다. 맨 앞에 두되 `unicode-range`로 범위를 좁혀놨으니 나머지 글자는 자동으로 다음 폰트로 폴백된다. 본문 글꼴은 그대로다.

### 직접 만들지 말고 기성 폰트를 쓴다

컬러 이모지 폰트를 통째로 받으면 수 MB다. 직접 서브셋하는 대신, 국기 글리프만 담은 COLR/CPAL 폰트가 이미 나와 있다. `country-flag-emoji-polyfill` 같은 패키지가 그 폰트(약 78KB)와 주입 로직을 함께 제공한다.

```js
import { polyfillCountryFlagEmojis } from 'country-flag-emoji-polyfill';

// 클라이언트에서 한 번 호출 — <style>에 @font-face를 주입한다
polyfillCountryFlagEmojis('Twemoji Country Flags', '/fonts/TwemojiCountryFlags.woff2');
```

이 라이브러리가 해주는 게 두 가지 있는데, 둘 다 직접 만들면 은근히 번거롭다.

canvas로 지원 여부를 먼저 검사한다. 같은 문자를 흰색·검은색으로 각각 그려서 픽셀을 비교한다. 컬러 이모지로 그려졌다면 두 결과가 같고, 글자로 그려졌다면 다르다. 이 검사로 "이모지는 되는데 국기는 안 되는" 환경만 골라낸다. 이미 국기가 보이는 환경에서는 폰트를 아예 주입하지 않으므로 불필요한 다운로드가 없다.

태그 시퀀스 국기까지 범위에 넣는다. 잉글랜드·스코틀랜드·웨일스 깃발은 Regional Indicator가 아니라 다른 방식(U+1F3F4 + 태그 문자)이라 범위를 따로 잡아줘야 한다.

```
unicode-range: U+1F1E6-1F1FF,              /* 일반 국기 */
               U+1F3F4, U+E0062-E007F      /* 태그 시퀀스 국기 */
```

### 폰트는 자체 호스팅하는 게 낫다

이런 라이브러리는 대개 폰트 URL 기본값이 공개 CDN이다. 편하지만 가용성과 지연을 내가 통제할 수 없다. 특히 주 사용자층이 CDN 엣지에서 먼 지역이면 체감 차이가 난다. 대부분 URL 오버라이드를 지원하므로, 패키지에 동봉된 woff2를 정적 디렉터리로 복사해 자기 도메인에서 서빙하는 게 좋다.

### 이 방식의 장점

DOM을 건드리지 않는다. 사용자가 작성한 글이든 UI 문구든, 화면 어디에 나타나도 자동으로 적용된다. 렌더링 로직·마크다운 파서와 충돌하지 않고 리렌더와도 싸우지 않는다.

적용 지점이 두 곳뿐이다. 폴리필 호출 한 줄과 폰트 스택 한 줄. 되돌리기도 쉽다.

## 5. 해결책 B — 이미지로 치환

텍스트에서 국기 시퀀스를 찾아 `<img>`로 바꾸는 방식이다. 이모지를 이미지로 갈아끼우는 라이브러리들이 쓰는 접근이기도 하다.

```js
// 국기 시퀀스 → ISO 국가 코드
function toCountryCode(seq) {
  return [...seq]
    .map((c) => String.fromCharCode(c.codePointAt(0) - 0x1f1e6 + 0x41))
    .join('')
    .toLowerCase();          // 🇰🇷 → 'kr'
}
```

국가 플래그 SVG 세트를 이미 갖고 있는 프로젝트라면(국가 선택 UI가 있으면 대개 있다) 외부 의존성 없이 재사용할 수 있다는 게 매력이다.

대신 대가가 있다.

- 런타임 처리가 들어간다. 사용자 텍스트를 순회하며 치환해야 한다
- 마크다운·링크 파서와 순서를 맞춰야 한다. 치환을 먼저 하면 파서가 이미지 태그를 다시 건드리고, 나중에 하면 이미 HTML이 된 문자열을 다뤄야 한다
- XSS를 신경 써야 한다. 사용자 입력을 HTML로 조립하는 경로가 생기므로, 반드시 이스케이프된 텍스트 노드 단위로 처리해야 한다

모든 환경에서 픽셀 단위로 동일하게 보인다는 게 유일하면서도 확실한 장점이다. 디자인 일관성이 중요한 서비스가 아니라면 A가 낫다.

---

## 6. 해결책 C — 그냥 두기

진지하게 선택지다. no cap. 판단 기준은 Windows 데스크톱 사용자 비중 하나다.

모바일 중심 서비스라면 영향받는 사용자가 극소수다. 분석 도구의 기기·OS 분포를 먼저 보고, 유의미할 때만 A로 가는 게 합리적이다. 측정 없이 폰트부터 붙이는 건 순서가 뒤집힌 것이다.

## 7. 정리

| | 방법 | 비용 | 결과 |
| --- | --- | --- | --- |
| A | 국기 전용 폰트 + `unicode-range` | 낮음 (호출 1줄 + 폰트 스택 1줄) | 필요한 환경에서만 국기 표시 |
| B | 이미지 치환 | 중간 (런타임 + 보안 검토) | 모든 환경 동일 |
| C | 방치 | 0 | Windows 일부 사용자만 글자로 봄 |

기억할 것 세 가지.

국기는 문자 두 개다. 이걸 알면 "왜 어떤 이모지는 되고 국기만 안 되나"가 바로 설명된다.

렌더링 문제와 데이터 문제를 먼저 가른다. 코드포인트를 찍어보면 5초면 갈린다. 이 단계를 건너뛰면 DB와 인코딩을 며칠 파게 된다.

`unicode-range`는 이런 국소 대응에 아주 잘 맞는다. 특정 문자 구간만 다른 폰트로 넘기는 건 국기 말고도 쓸 데가 많다 — 숫자만 다른 폰트로 쓰거나, 특정 언어 구간만 교체하거나.

사이트맵에 225개 URL을 담아 제출했다. 나흘 뒤 검색 콘솔을 보니 색인된 건 딱 1개였다. 마케팅에서 "개별 페이지마다 수동 색인을 걸어야 하는 것 아니냐"는 문의가 왔다.

결론부터: 수동 색인은 필요 없었다. 대신 진단해보니 원인이 세 갈래로 갈렸고, 그중 하나는 "기다리면 되는 것", 하나는 "기다려도 안 되는 것", 하나는 "안 돼도 상관없는 것"이었다. 이걸 가르는 게 이 기록의 핵심이다.

---

## 반전으로 시작하기

가장 먼저 확인한 건 "그 1개가 뭐냐"였다.

```
색인된 URL: https://example.com/es/app
```

그리고 사이트맵을 뒤져봤더니,

```bash
curl -s https://example.com/sitemap.xml -o s.xml
grep -c '<loc>' s.xml                                    # 225
grep -c '<loc>https://example.com/es/app</loc>' s.xml    # 0   ← ?
grep -c '<loc>https://example.com/es</loc>' s.xml        # 1
```

색인된 그 URL은 사이트맵에 없었다. 사이트맵에 있는 건 랜딩(`/es`)이고, 색인된 건 앱 메인(`/es/app`)이었다.

즉 상황은 "사이트맵 225개 중 1개가 색인됨"이 아니라 "사이트맵 URL은 아직 0개 색인, 그와 별개로 링크 타고 발견된 페이지 1개가 색인됨"이었다. 문제의 모양이 완전히 달라진다.

> 첫 단계는 항상 "보고된 숫자가 실제로 무엇을 세고 있는가"를 확인하는 것이다. 여기서 안 짚었으면 계속 엉뚱한 걸 봤다.

## 1. 죽은 가설 둘

### 가설 A — "제출한 사이트맵이 옛날 버전이었다"

며칠 전 사이트맵 생성 로직에 버그가 있어서 정적 페이지 21개만 나가던 시기가 있었다. 제출 시점이 그 수정 전이라면 상세 페이지를 애초에 못 봤을 것이다.

릴리즈 태그로 확인했다.

```bash
git tag --contains <수정_커밋> --sort=creatordate | head -3
# → release-<날짜>-v1.0.2   ← 제출 하루 전
```

수정은 제출 전날 배포됐다. 제출 시점에 이미 225개짜리였다. 가설 탈락.

> 이건 내가 앞서 "재제출이 필요하다"고 말했다가 뒤집은 부분이다. 배포 시각을 확인하지 않고 추측으로 말했던 것. 릴리즈 태그가 있으면 `git tag --contains`로 5초면 끝난다.

### 가설 B — "언어판이 중복 처리됐다"

`/en/app`, `/es/app`, `/pt/app`은 같은 페이지의 3개 언어판이다. 서로 다른 언어판임을 알려주는 `hreflang`이 없으면 Google이 중복으로 보고 하나만 남긴다 — 실제로 이 사이트엔 `hreflang`이 랜딩과 기사 상세에만 있었다.

그럴듯했지만 셋을 직접 비교해보니,

```
/en/app   서버 HTML 텍스트 373자 · 내부링크 5개
/es/app   서버 HTML 텍스트 465자 · 내부링크 5개
/pt/app   서버 HTML 텍스트 480자 · 내부링크 5개
```

구조가 동일하다. es가 선택될 기술적 이유가 없다. 게다가 세 언어판은 title/description이 각 언어로 달라서, Google이 굳이 중복으로 볼 근거도 약하다.

이 가설은 "왜 하나만"은 설명해도 "왜 나머지가 통째로 없나"는 설명하지 못했다. 그리고 실제 질문은 후자였다.

## 2. 진짜 원인 — 서버 HTML이 비어 있었다

사이트맵에 처음부터 들어 있던 목록 페이지가 왜 하나도 안 잡혔는지를 파고들었다.

```bash
curl -s https://example.com/en/app/list -o p.html
wc -c < p.html                                  # 90,660  ← 크기는 멀쩡
grep -oE '<h[1-3][^>]*>[^<]{4,60}' p.html       # (없음)
grep -oE 'href="/en/article/[^"]+"' p.html      # (없음)
```

HTML은 90KB인데 제목도 링크도 하나도 없다. 전부 스크립트와 스타일이고 본문이 없다. 데이터를 브라우저에서 받아 그리는 구조(CSR)라 서버가 내려주는 건 빈 껍데기다.

측정을 제대로 하려면 스크립트/스타일을 걷어내고 실제 텍스트만 재는 게 좋다.

```python
import re
h = open('p.html', encoding='utf-8', errors='ignore').read()
body = re.sub(r'(?is)<script.*?</script>|<style.*?</style>', '', h)
text = re.sub(r'\s+', ' ', re.sub(r'(?s)<[^>]+>', ' ', body)).strip()
print(len(text))   # ← 이 숫자가 크롤러가 보는 본문량
```

이 잣대로 사이트 전체를 재봤다.

| 페이지 | 서버 HTML 실제 텍스트 | 색인 |
| --- | --- | --- |
| 랜딩 `/{lang}` | 제목 태그 0개 | ✗ |
| 앱 메인 `/{lang}/app` | 373~480자 | es만 ○ |
| 정책 페이지 4종 (약관·개인정보 등) | 155~214자 | ✗ |
| 목록 페이지 2종 | 0 | ✗ |
| 기사 상세 150개 | 본문 있음 | 아직 |

약관 페이지가 157자라는 게 결정적이었다. 이용약관이 157자일 리 없다. 정책 페이지도 전부 CSR이었다.

정리하면 이 사이트에서 서버 HTML에 진짜 본문이 있는 건 기사 상세뿐이었다. 나머지는 전부 껍데기다. 그리고 색인된 `/es/app`은 껍데기 중에서 그나마 텍스트가 가장 많은 그룹에 속했다. 155자짜리 약관은 Google이 빈 페이지로 보고 버린 것이다.

> Google은 JS를 실행하긴 한다. 다만 2차 렌더링 대기열로 넘겨 나중에 처리하고, 그 사이 빈 페이지로 판단되면 "크롤링됨 – 색인 생성 안 함"에 남는다. "봇도 JS 돌린다"는 말은 "SPA도 SEO 괜찮다"는 뜻이 아니다.

## 3. 곁다리로 나온 중복 문제

색인된 `/es/app`과 사이트맵에 있는 `/es`를 나란히 놓고 봤다.

```
/es       title: Brand | 서비스 한 줄 소개    canonical: /es    본문 제목 0개
/es/app   title: Brand | 서비스 한 줄 소개    canonical: 없음   본문 제목 3개
                 ↑ 글자 하나 다르지 않음 (description도 동일)
```

title과 description이 완전히 같았다. Google 입장에선 같은 페이지 2개다. 중복이면 하나만 색인하고, 어느 쪽을 남길지는 Google이 정한다.

여기서 `/es`는 서버 HTML에 본문이 없고 `/es/app`은 조금이라도 있었다. 그래서 내용이 있는 쪽이 대표로 뽑혔고, 사이트맵에 넣은 `/es`가 탈락했다. 사이트맵에 없는 URL이 색인된 경위가 이거다.

검색 콘솔에서 이런 상태는 "대체 페이지(적절한 표준 태그가 있는 중복 페이지)"로 표시된다. "중복이라 색인 안 했고, 대신 저쪽을 넣었다"는 뜻이다.

리다이렉트 때문인가 싶어 확인했지만 아니었다.

```bash
curl -s -o /dev/null -w "%{http_code} → %{redirect_url}\n" https://example.com/es
# 200 →          ← 리다이렉트 없음
```

## 4. 색인을 막는 설정은 없었다

원인을 좁히기 전에 "차단당한 것"부터 배제해야 한다. 이건 몇 초면 된다.

```bash
curl -s https://example.com/robots.txt          # Allow: / · 사이트맵 선언 있음
curl -s https://example.com/pt/article/<slug> -o d.html -w "%{http_code}\n"   # 200
grep -oE '<meta name="robots"[^>]*>' d.html     # (없음 = noindex 없음)
grep -oE '<link rel="canonical"[^>]*>' d.html   # 자기 자신 가리킴
```

전부 정상. 기사 상세는 색인을 막는 요소가 하나도 없었다. 그냥 아직 안 된 것뿐이다.

제출일과 크롤링 시작일 사이에도 사흘이 있었고, 크롤링이 시작된 지는 하루째였다. 발견 → 크롤링 → 색인은 각각 별개 단계고, 마지막 단계는 보통 몇 주 걸린다. 신규 도메인이 사이트맵 냈다고 며칠 만에 다 들어가지 않는다.

## 5. 셋으로 갈라 답하기

이 진단의 결론은 "고쳐야 할 것"과 "기다릴 것"과 "안 해도 될 것"을 나눈 것이다.

| 대상 | 판정 | 근거 |
| --- | --- | --- |
| 기사 상세 150개 | 기다린다 | 서버 렌더 정상, 차단 없음. 시간 문제 |
| 목록·정책 페이지 | 기다려도 안 됨 | 서버 HTML이 빈 껍데기. 구조 문제 |
| 랜딩 vs 앱 메인 중복 | 선택 사항 | title/description 분리하면 풀림 |

그리고 "기다려도 안 되는 것"이라고 다 고쳐야 하는 건 아니다.

목록 페이지는 아무도 "브랜드명 + 목록"으로 검색하지 않는다. 실제 검색 유입은 기사 제목이나 고유명사로 들어오고, 그건 상세 페이지가 받는다. 상세는 이미 사이트맵에 전부 있고 서버 렌더도 정상이다. 약관 페이지도 마찬가지로 검색될 이유가 없다 — 사람이 브라우저로 보는 건 정상이니까.

다만 하나 걸리는 게 있다. 목록 페이지의 서버 HTML에 상세로 가는 링크가 0개라 상세 페이지들이 사이트맵으로만 발견되는 "고아 페이지" 상태다. Google은 내부 링크를 중요도 신호로 쓴다. 그래서 목표를 다시 쓰면 *"목록 페이지를 색인시키기"*가 아니라 *"상세로 가는 링크를 크롤러에게 보여주기"*가 된다. 상세 색인이 정상적으로 늘면 안 해도 되고, 지지부진하면 그때 손대면 된다.

수동 색인은 마지막 카드다. 구조 문제가 남아 있는 상태에서 수동 색인을 걸어봐야 같은 판정이 반복된다. 순서는 ①구조 확인 → ②정상인 것 기다리기 → ③그래도 안 늘면 수동.

## 남는 것

보고된 숫자가 뭘 세는지부터 확인한다. "225개 중 1개"와 "0개 + 별개의 1개"는 완전히 다른 문제다. 이걸 안 짚었으면 사이트맵 쪽을 계속 팠을 것이다.

추측으로 배포 시점을 말하지 않는다. "제출 시점엔 옛날 버전이었을 것"이라고 했다가 태그 확인하고 뒤집었다. `git tag --contains <커밋>`은 5초다. 5초짜리 확인을 건너뛴 추측이 남의 시간을 쓴다.

SPA의 SEO 진단은 "서버 HTML의 실제 텍스트량"에서 시작한다. HTML 파일 크기는 아무것도 말해주지 않는다 — 90KB짜리가 본문 0자일 수 있다. 스크립트·스타일·태그를 걷어내고 남은 글자 수를 재면 크롤러가 뭘 보는지 그대로 나온다. 약관이 157자라는 한 줄이 전체 그림을 바꿨다.

title과 description이 같은 두 URL은 같은 페이지다. 사람 눈에 다른 페이지여도 그렇다. 그리고 중복일 때 어느 쪽을 남길지는 내가 아니라 Google이 정한다. `canonical`을 안 달아두면 그 선택에 개입할 수단이 없다.

차단 여부는 원인 탐색 전에 배제한다. robots.txt, `noindex` 메타, canonical, HTTP 상태 — 네 개 확인에 1분이면 된다. 이걸 먼저 끝내야 "설정 문제"와 "시간 문제"와 "구조 문제"를 가를 수 있다.

"안 됨"이 항상 "고쳐야 함"은 아니다. 색인 안 되는 페이지 목록을 그대로 할 일 목록으로 옮기면 검색 가치도 없는 약관 페이지를 SSR로 바꾸는 데 시간을 쓰게 된다. 각 페이지가 검색에서 무슨 역할을 하는지 먼저 정해야 한다.
